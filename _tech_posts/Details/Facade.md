# [퍼사드 패턴(Facade Pattern)]

퍼사드(Facade)는 건물의 '정면'을 뜻하는 프랑스어 'Façade'에서 유래한 용어다. 건축에서 건물의 복잡한 내부 배관이나 골조를 뒤로하고 정면의 깔끔한 외벽만 보여주는 것처럼, 소프트웨어 공학에서의 퍼사드 패턴 역시 **복잡한 내부 서브시스템들을 뒤로 감추고 사용자가 쉽게 접근할 수 있는 단순화된 하나의 통합 인터페이스를 제공하는 구조적 디자인 패턴**이다.

개발을 진행하며 시스템이 커질수록 내부 클래스는 늘어나고 하위 모듈 간의 인터페이스는 복잡해진다. 클라이언트가 이러한 하위 시스템의 다양한 기능을 직접 조작하려고 하면, 알아야 할 메서드가 많아지고 시스템 간의 결합도(Coupling)가 높아져 코드의 가독성과 유지보수성이 급격히 떨어진다. 퍼사드 패턴은 이러한 문제를 해결하기 위해 시스템의 복잡한 경로 앞에 단순한 대문 역할을 하는 '퍼사드 클래스'를 두는 방식을 취한다.

## 퍼사드 패턴의 주요 특징과 장점

* **낮은 결합도와 의존성 격리**: 클라이언트는 복잡한 내부 서브시스템의 구체적인 구현이나 존재를 세세하게 알 필요 없이 오직 퍼사드 클래스하고만 소통한다. 이로 인해 서브시스템 내부의 코드가 변경되거나 외부 외부 라이브러리가 교체되더라도 클라이언트 코드는 아무런 영향을 받지 않는다.
* **가독성과 편의성 향상**: 수많은 단계의 전처리, 옵션 설정, 연쇄적인 API 호출 과정을 퍼사드 내부 메서드 하나로 압축할 수 있다. 클라이언트 코드가 극도로 단순해지며, 복잡한 시스템을 처음 접하는 개발자도 진입 장벽 없이 기능을 안전하게 활용할 수 있게 된다.
* **서브시스템의 직접 접근 허용**: 퍼사드 패턴은 내부 구조를 강제로 꽁꽁 숨기는 캡슐화가 아니다. 퍼사드가 제공하는 거대한 기능 외에 더 세부적인 제어가 필요한 숙련된 개발자라면, 언제든지 퍼사드를 거치지 않고 하위 시스템의 클래스에 직접 접근하여 정밀한 조작을 수행할 수 있는 유연성을 열어둔다.

## 퍼사드 패턴의 구조적 예시

예를 들어 영화를 감상하기 위해 홈시어터 시스템을 가동하는 로직을 개발한다고 가정하자. 퍼사드 패턴을 적용하지 않으면 클라이언트는 전등 클래스를 찾아 불을 어둡게 조절하고, 빔프로젝터를 켜고, 스크린을 내리고, 사운드 바의 볼륨을 조정하는 등 개별 객체를 모두 생성하고 각각의 메서드를 순차적으로 직접 호출해야 한다.

반면 퍼사드 패턴을 도입하면 `HomeTheaterFacade`라는 하나의 클래스를 정의하고, 내부에 `watchMovie()`라는 고수준 메서드를 구현한다. 이 `watchMovie()` 메서드가 내부적으로 조명, 프로젝터, 스크린, 오디오 클래스를 적절한 순서대로 제어하도록 위임하는 구조다. 결과적으로 클라이언트는 복잡한 기기 제어 과정을 신경 쓸 필요 없이 단 한 줄의 코드로 원하는 목적을 달성하게 된다.

다만 모든 복잡성을 하나의 퍼사드 클래스에 무비판적으로 몰아넣다 보면, 해당 클래스가 지나치게 비대해져 홀로 모든 책임을 떠안는 '갓 클래스(God Class)'가 될 위험이 있다. 따라서 하위 서브시스템의 논리적 경계와 책임 분할을 명확히 고려하며 적절한 규모로 설계하는 것이 중요하다.
