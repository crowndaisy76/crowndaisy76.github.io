이전 글에서는 자바스크립트 난독화의 표준인 javascript-obfuscator가 코드를 은닉하는 3단계 파이프라인과 그 내부 메커니즘을 분석했다.

이번 글에서는 이에 대응하여, 난독화된 스크립트를 AST 레벨에서 정밀하게 추적하고 본래의 구조로 복원해 내는 강력한 역난독화 도구인 synchrony의 아키텍처와 구동 원리를 분석한다.

# synchrony 분석

synchrony의 역난독화 과정은 javascript-obfuscator가 코드를 난독화한 과정을 거꾸로 되짚어가는 메커니즘을 따른다. 난독화 도구가 문법 노드를 쪼개고 분산시켰다면, synchrony는 이들의 종속성과 실행 흐름을 추적하여 원래의 형태로 수렴시키는 방식을 취한다.

전체적인 과정은 크게 네 가지 단계로 진행된다.

1. **Parsing**: 텍스트 형태의 난독화 코드를 분석 가능한 구조적 데이터인 AST로 재구성하는 단계다. 자바스크립트 생태계의 대표적인 컴파일러 툴킷인 `@babel/parser`를 채택하여 수만 개의 노드 객체로 매핑하며, 이 단계가 완료되어야 문법 레벨에서의 정밀 트래킹이 가능해진다.

2. **Context Initialization**: 정적 분석의 한계를 극복하기 위해 가상의 격리된 런타임 환경을 준비하는 과정이다. 암호화된 문자열 배열과 이를 복호화하는 런타임 프록시 함수들을 식별한 뒤, 해당 로직을 가상 환경에서 사전 실행하여 해독된 평문 데이터를 메모리에 캐싱하는 분석 컨텍스트를 구축한다.

3. **Transformation**: 동작의 핵심이 되는 단계로, 내부적으로 정의된 수십 개의 독립적인 Babel 플러그인(Transformer) 시퀀스가 AST를 순회하며 난독화 패턴을 해제한다. 앞서 확보한 컨텍스트를 기반으로 난독화된 함수 호출을 실제 문자열로 환원하고, 거대한 `switch-case` 덩어리로 찢겨 있던 제어 흐름 평탄화 구조를 역추적하여 본래의 선형적 실행 구조로 조립한다.

4. **Code Generation**: 모든 변환 플러그인을 통과하여 본래의 논리가 복원된 AST를 다시 실행 가능한 자바스크립트 소스코드 문자열로 환원한다. `@babel/generator`를 사용하여 난독화 과정에서 임의로 소멸되었던 들여쓰기, 줄바꿈 등의 포맷팅을 규격에 맞게 재배치함으로써 최종적인 역난독화 결과물을 도출한다.

## 1. Parsing

역난독화 파이프라인의 첫 단추는 텍스트 형태의 난독화 소스코드를 분석 및 제어가 가능한 데이터 구조인 AST로 변환하는 단계다. 문법 단위로 파편화된 노드 구조가 확보되어야만 이후 단계에서 난독화 패턴을 정밀하게 추적하고 수정할 수 있다.

여기서 주목할 점은 난독화 도구인 javascript-obfuscator가 가볍고 빠른 ESTree 규격의 `acorn` 파서를 사용하는 반면, 역난독화 도구인 synchrony는 Babel 툴킷(`@babel/parser`)을 채택하고 있다는 것이다. 이는 단순 구문 분석을 넘어 '코드 복원'이라는 목적을 달성하기 위한 아키텍처적 선택이다.

`acorn`이 생성하는 순수 ESTree AST는 단순히 부모-자식 노드의 연결 관계만 보여주기 때문에 식별자 추적이 어렵다. 반면 Babel은 각 노드의 유효 범위와 변수의 선언 및 참조 관계를 완전히 추적할 수 있는 `Scope`와 `NodePath` API를 기본적으로 제공하므로, 식별자 맹글링을 역추적하여 원본 이름을 복원해야 하는 역난독화에 절대적으로 유리하다. 또한 특정 노드가 최종적으로 어떤 값으로 수렴하는지 계산해 주는 정적 평가(`path.evaluate()`) 엔진이 내장되어 있어, 암호화된 수식이나 난독화 코드를 해독하는 로직을 구현하기에 최적화되어 있다.

synchrony 내부에서 입력된 소스코드를 Babel AST로 파싱하는 핵심 로직은 `src/deobfuscator.ts` 파일에 구현되어 있다. 실제 프로젝트 아키텍처 규격에 따른 구현 형태는 다음과 같다.

```typescript
import { parse, ParserOptions } from '@babel/parser';
import * as babel from '@babel/core';

export class Deobfuscator {
    /**
     * 난독화된 자바스크립트 소스코드를 파싱하여 Babel AST를 반환한다.
     * @param {string} sourceCode - 원본 난독화 텍스트
     * @returns {babel.types.File} 생성된 Babel AST 객체
     */
    public parseSource(sourceCode: string): babel.types.File {
        const parserOpts: ParserOptions = {
            sourceType: 'module',
            allowReturnOutsideFunction: true,
            allowImportExportEverywhere: true,
            plugins: [
                'asyncGenerators',
                'bigInt',
                'classProperties',
                'classPrivateProperties',
                'dynamicImport',
                'importMeta',
                'objectRestSpread'
            ]
        };

        return parse(sourceCode, parserOpts);
    }
}

```

#### 코드 및 동작 메커니즘 분석

* **유연한 구문 허용 (Loosened Parsing)**: 난독화된 스크립트 특유의 기형적인 구조에 대응하기 위해 문법적 예외 처리를 활성화한다. `allowReturnOutsideFunction`이나 `allowImportExportEverywhere` 같은 옵션을 통해 모듈 스코프 바깥에 `return`문이 박혀 있는 등의 상황에서도 구문 오류 없이 안정적으로 트리를 추출한다.
* **최신 ECMAScript 플러그인 확장**: `plugins` 배열에 `bigInt`, `classProperties`, `dynamicImport` 등 현대 자바스크립트 명세들을 대거 포함한다. 이는 javascript-obfuscator가 가공해 놓은 최신 문법 기반의 난독화 기법들을 누락 없이 완벽하게 객체 노드로 수집하기 위한 방어적 설계다.

이 단계를 거쳐 텍스트 소스코드는 구조화된 Babel 노드 데이터로 재조립되며, 파이프라인은 정적 해독이 불가능한 런타임 암호화 영역을 깨부수기 위한 Context Initialization 단계로 이어진다.

## 2. Context Initialization

정적 분석만으로는 해독이 불가능한 런타임 암호화 영역을 처리하기 위해 가상의 실행 환경을 구축하고 초기화하는 단계다. javascript-obfuscator에 의해 난독화된 스크립트는 중요 문자열 리터럴들을 하나의 배열(`StringArray`)에 모아두고, Base64나 RC4 등으로 암호화한 뒤 런타임 프록시 함수를 거쳐 실시간으로 복호화하도록 설계되어 있다. 이 때문에 단순히 AST 노드를 텍스트로 읽는 것만으로는 본래의 데이터를 알아낼 수 없다.

synchrony는 이를 해결하기 위해 정적 분석 과정 중에 직접 난독화 스크립트 내부의 복호화 함수를 실행하여 평문 문자열을 미리 확보하는 방식을 취한다. AST 트리를 순회하며 문자열 배열과 이와 연결된 복호화 프록시 노드들을 식별한 뒤, 안전하게 격리된 가상 머신 컨텍스트 상에서 해당 로직을 사전 실행하여 해독된 데이터 매핑 테이블을 메모리에 캐싱한다.

synchrony 내부에서 이러한 가상 런타임 환경을 생성하고 분석 컨텍스트를 설계하는 핵심 로직은 `src/context.ts` 파일에 구현되어 있다. 실제 프로젝트 아키텍처 규격에 따른 구현 형태는 다음과 같다.

```typescript
import * as vm from 'vm';
import * as babel from '@babel/core';
import { generate } from '@babel/generator';

export class DeobfuscationContext {
    private vmContext: vm.Context;

    constructor() {
        // 격리된 Node.js VM 컨텍스트 초기화
        this.vmContext = vm.createContext({
            console: console,
            Buffer: Buffer
        });
    }

    /**
     * 식별된 복호화 함수 노드를 자바스크립트 코드로 변환하여 VM 내부에서 실행한다.
     * @param {babel.types.Node} node - 복호화 대상 AST 노드
     */
    public evaluateNode(node: babel.types.Node): void {
        // AST 노드를 실행 가능한 문자열 코드로 변환
        const { code } = generate(node);
        
        try {
            // 가상 머신 스코프 내에서 안전하게 실시간 코드를 주입 및 실행
            vm.runInContext(code, this.vmContext);
        } catch (error) {
            // 런타임 평가 실패 시 예외 처리 로직
        }
    }
}

```

#### 코드 및 동작 메커니즘 분석

* **격리된 VM 컨텍스트 생성**: Node.js의 내장 모듈인 `vm`을 활용하여 가상 머신 스코프를 생성한다. `vm.createContext()`를 통해 메인 프로세스의 전역 오염 없이 안전하게 외부 스크립트 노드를 실행할 수 있는 독립된 환경을 마련하며, 복호화 연산에 필수적인 `Buffer` 객체 등을 바인딩한다.
* **AST 기반 동적 코드 평가 (Evaluation)**: 탐색된 `StringArray` 및 디코딩 로직 노드를 `@babel/generator`를 통해 임시 문자열 코드로 환원한다. 이후 `vm.runInContext()`를 호출하여 가상 환경 안에서 실시간으로 로직을 가동시킨다. 이 과정을 통해 생성된 평문 문자열들은 복호화 함수 이름과 매핑되어 컨텍스트 내부에 안전하게 저장된다.

이 단계를 거쳐 런타임에 은닉되어 있던 동적 문자열 데이터가 정적으로 매핑 가능한 상태로 완전히 전환되며, 파이프라인은 이 매핑 테이블을 기반으로 실제 AST 트리를 가공하는 Transformation 단계로 이어진다.

## 3. Transformation

Parsing 단계를 거쳐 생성된 AST는 곧바로 뒤틀린 구조를 복원하고 코드를 단순화하는 역난독화 파이프라인으로 진입한다. synchrony는 단일 연산으로 해독하기 어려운 복잡한 패턴들을 정밀하게 처리하기 위해, 내부적으로 정의된 총 9개의 독립적인 코어 트랜스포머 시퀀스를 순차적으로 가동한다.

각 트랜스포머는 객체 속성 접근자 정리, 제어 흐름 복구, 문자열 배열 해독 등 특정 난독화 기법을 개별적으로 타깃팅하여 무력화하도록 설계된 전용 부품이다. 이들은 분석 컨텍스트를 기반으로 트리를 추적하며, 이전 단계의 복원 결과가 다음 단계의 입력 기틀이 되는 유기적인 흐름을 형성하여 꼬여 있는 코드를 점진적으로 풀어낸다.

### Stage 1: Desequence

Transformation 파이프라인의 첫 번째 트랜스포머는 `Desequence`다. 이 단계는 소스코드 전반에 걸쳐 기형적으로 묶여 있는 쉼표 연산자(`SequenceExpression`) 구조를 파싱하여 개별 문장으로 분해하는 역할을 수행한다.

javascript-obfuscator는 코드를 분석하기 어렵게 만들기 위해 여러 줄로 구성된 정상적인 구문들을 쉼표(,)를 이용해 강제로 한 줄의 연산식으로 압축하는 "Stage 9: Simplifying"를 가동한다. Desequence는 바로 이 Simplifying 단계를 무력화한다. 복잡하게 나열된 쉼표 연산자 구조가 먼저 해체되어야만, 이후 진입할 트랜스포머들이 문법 노드를 정확하게 인식하고 추적할 수 있는 밑바탕이 마련된다.

해당 로직은 `src/transformers/desequence.ts` 파일에 구현되어 있으며, AST를 순회하며 쉼표 연산자를 독립된 실행문으로 재조립하는 핵심 메커니즘은 다음과 같다.

```typescript
import { Transformer } from './transformer';
import * as babel from '@babel/core';

export class Desequence extends Transformer {
    /**
     * SequenceExpression(쉼표 연산자)을 탐색하여 다중 ExpressionStatement로 분해한다.
     */
    public static readonly visitor: babel.Visitor = {
        ExpressionStatement(path) {
            const { node } = path;
            
            // 실행문 내부가 쉼표 연산자(SequenceExpression)로 이루어져 있는지 검증
            if (!babel.types.isSequenceExpression(node.expression)) {
                return;
            }

            const expressions = node.expression.expressions;
            const replacementNodes: babel.types.Statement[] = [];

            // 쉼표로 연결된 개별 표현식들을 독립된 실행문 노드로 변환
            for (const expr of expressions) {
                replacementNodes.push(babel.types.expressionStatement(expr));
            }

            // 기존의 한 줄짜리 노드를 분해된 다중 라인 노드 배열로 최종 치환
            path.replaceWithMultiple(replacementNodes);
        }
    };
}

```

#### 코드 및 동작 메커니즘 분석

* **쉼표 표현식 추출 및 검증**: AST를 탐색하며 문장 단위 노드인 `ExpressionStatement`를 포착한다. 이후 해당 문장의 내부 알맹이가 쉼표로 연결된 `SequenceExpression` 구조인지 확인하고, 조건을 만족하면 연결된 서브 표현식(`expressions`) 배열을 통째로 수집한다.
* **선형적 다중 노드 치환**: 추출한 개별 표현식들을 순회하며 각각을 독립적인 문장 형태인 `ExpressionStatement` 노드로 재포장한다. 마지막으로 Babel의 `path.replaceWithMultiple()` API를 호출하여 원래 한 줄 속에 묶여 있던 거대한 쉼표 덩어리를 여러 줄의 순차적인 실행문 배열로 강제 분리한다.

이 단계를 통해 일차적으로 구문들의 경계선이 명확해지며, 파이프라인은 복잡한 논리식과 수식을 정적으로 계산해 나가는 다음 트랜스포머 단계로 이어진다.

### Stage 2: Simplify

Desequence 단계를 거쳐 쉼표 연산자가 분해되면, 파이프라인은 파편화된 연산식과 제어 로직을 정적으로 계산하여 최적화하는 Simplify 단계로 진입한다. 이 단계는 정적 분석을 방해하기 위해 잘게 쪼개진 수학적 수식이나 난해하게 꼬인 조건문을 단순화하는 역할을 수행한다.

javascript-obfuscator는 소스코드를 읽기 어렵게 만들기 위해 이진 연산식을 계산 가능한 복잡한 수식으로 분할하는 "Stage 6: Converting" 단계를 수행하고, 최적화 단계에서 `if` 문을 `!![] && ...` 같은 형태의 논리 연산자로 압축하는 "Stage 9: Simplifying"을 가동한다. Simplify 트랜스포머는 이 두 단계를 동시에 무력화한다. 난독화 도구가 꼬아놓은 연산들을 정적으로 미리 평가하여 최종 리터럴 상수로 환원함으로써 코드의 가독성을 극대화한다.

해당 로직은 `src/transformers/simplify.ts` 파일에 구현되어 있으며, 복잡한 논리 및 수식 노드를 계산하여 단일 리터럴 노드로 치환하는 핵심 메커니즘은 다음과 같다.

```typescript
import { Transformer } from './transformer';
import * as babel from '@babel/core';

export class Simplify extends Transformer {
    /**
     * 정적 평가가 가능한 표현식 노드를 탐색하여 단일 리터럴 상수로 축소한다.
     */
    public static readonly visitor: babel.Visitor = {
        'BinaryExpression|UnaryExpression|LogicalExpression'(path) {
            // Babel 내장 기능을 이용해 해당 노드가 정적으로 계산 가능한지 평가
            const evaluated = path.evaluate();

            // 계산 결과가 불확실하거나 보안상 안전하지 않은 경우 생략
            if (!evaluated.confident) {
                return;
            }

            const value = evaluated.value;
            let literalNode;

            // 평가된 값의 타입에 맞는 Babel 리터럴 노드 생성
            if (typeof value === 'number') {
                literalNode = babel.types.numericLiteral(value);
            } else if (typeof value === 'string') {
                literalNode = babel.types.stringLiteral(value);
            } else if (typeof value === 'boolean') {
                literalNode = babel.types.booleanLiteral(value);
            } else if (value === null) {
                literalNode = babel.types.nullLiteral();
            }

            // 생성된 명확한 리터럴 노드가 있다면 기존의 복잡한 연산 노드를 치환
            if (literalNode) {
                path.replaceWith(literalNode);
            }
        }
    };
}

```

#### 코드 및 동작 메커니즘 분석

* **정적 표현식 탐색 및 평가**: AST를 순회하며 이진 연산(`BinaryExpression`), 단항 연산(`UnaryExpression`), 논리 연산(`LogicalExpression`) 노드들을 포착한다. 이후 Babel의 강력한 내장 API인 `path.evaluate()`를 호출하여 런타임 실행 없이도 해당 연산식이 최종적으로 어떤 값으로 수렴하는지 컴파일 레벨에서 정밀하게 계산한다.
* **보안 검증 및 리터럴 환원**: `evaluated.confident` 플래그를 검증하여 연산의 결과가 100% 확정적이고 안전한지 확인한다. 조건이 충족되면 결과값의 원시 타입(`number`, `string`, `boolean` 등)을 분석하여 그에 매핑되는 가장 단순한 리터럴 상수의 형태로 노드를 재조립한 뒤 `path.replaceWith()`를 통해 기존의 복잡한 연산식 노드를 단일 값으로 덮어쓴다.

이 단계를 거치며 `0x1a2b * 0x2 + 0x3`이나 `![]` 같은 난해한 연산식들이 숫자가 가리키는 실제 리터럴 상수로 완전히 환원되며, 파이프라인은 의도적으로 주입된 가짜 분기문들을 잘라내는 DeadCode 단계로 이어진다.

### Stage 3: DeadCode

Simplify 단계를 거쳐 수식과 조건문이 단순화되면, 파이프라인은 무작위로 주입된 가짜 코드 분기를 판별하여 잘라내는 DeadCode 단계로 진입한다. 이 단계는 정적 분석의 공간 복잡도를 폭발적으로 증가시키는 죽은 코드들을 제거하는 역할을 수행한다.

javascript-obfuscator는 실행 흐름을 교란하고 분석가에게 혼란을 주기 위해 절대 실행되지 않는 무의미한 더미 로직을 삽입하는 "Stage 3: DeadCodeInjection"을 가동한다. DeadCode 트랜스포머는 바로 이 단계를 무력화한다. 앞선 단계에서 조건문 내부의 연산식이 `true` 또는 `false` 리터럴로 명확히 정리되었기 때문에, 이를 기반으로 실행 불가능한 가짜 경로(Dead Path)를 정밀하게 파악하여 트리에서 완전히 격리한다.

해당 로직은 `src/transformers/deadcode.ts` 파일에 구현되어 있으며, 무조건적인 분기문을 판별하여 불필요한 블록을 제거하는 핵심 메커니즘은 다음과 같다.

```typescript
import { Transformer } from './transformer';
import * as babel from '@babel/core';

export class DeadCode extends Transformer {
    /**
     * IfStatement를 탐색하여 항상 참 또는 거짓인 분기문의 가짜 경로를 잘라낸다.
     */
    public static readonly visitor: babel.Visitor = {
        IfStatement(path) {
            const { node } = path;

            // 조건식이 명확한 Boolean 리터럴 노드인지 검증
            if (!babel.types.isBooleanLiteral(node.test)) {
                return;
            }

            const isTrueMatch = node.test.value === true;

            if (isTrueMatch) {
                // 조건이 항상 참이면 원래의 if 블록(consequent)으로 노드를 대체
                path.replaceWith(node.consequent);
            } else {
                // 조건이 항상 거짓이면 else 블록이 존재할 때만 해당 블록으로 대체
                if (node.alternate) {
                    path.replaceWith(node.alternate);
                } else {
                    // else 블록도 없다면 문장 자체를 트리에서 삭제
                    path.remove();
                }
            }
        }
    };
}

```

#### 코드 및 동작 메커니즘 분석

* **조건식 평가 및 고정 분기 검증**: AST를 탐색하며 `IfStatement` 노드를 식별한 뒤, 조건절인 `test` 프로퍼티가 `BooleanLiteral`인지 검사한다. 정적 계산을 통해 `if (true)` 혹은 `if (false)` 형태로 고정된 분기점을 확보하면, 실질적인 데드 코드 제거 로직을 활성화한다.
* **AST 트리 최적화 및 제거**: 조건이 참일 경우 가짜 경로인 `else` 블록(`alternate`)을 파괴하고 진짜 로직인 `consequent` 블록만 남긴다. 반대로 조건이 거짓일 경우 `if` 블록을 통째로 걷어내고 `else` 블록으로 치환하거나, 하위 로직이 없다면 `path.remove()`를 호출하여 해당 조건문 전체를 구조적으로 도려낸다.

이 단계를 거치며 소스코드 곳곳에 심어져 있던 거대한 더미 코드 덩어리들이 소멸하여 순수한 비즈니스 로직만 남게 되며, 파이프라인은 문자열 해독 함수를 추적하기 위해 진입로를 다듬는 Demangle 단계로 이어진다.

### Stage 4: Demangle

DeadCode 단계를 거쳐 가짜 분기들이 정리되면, 파이프라인은 문자열 디코딩의 전초 기지 역할을 하는 Demangle 단계로 진입한다. 이 단계는 복잡하게 래핑된 프록시 함수 구조를 정형화하여 후속 트랜스포머가 암호화된 문자열의 위치를 정확하게 추적할 수 있도록 징검다리를 놓는 역할을 수행한다.

javascript-obfuscator는 추출한 문자열 배열에 직접 접근하지 못하도록 수많은 은닉형 래퍼 함수를 레이어 형태로 중첩 배치하는 "Stage 8: StringArray" 단계를 가동한다. Demangle 트랜스포머는 바로 이 은닉 기법의 외곽 프록시 장치들을 무력화한다. 식별자 껍데기를 파싱하고 정규화함으로써, 파이프라인이 소스코드에 흩어진 난독화 해독 함수의 본질을 직관적으로 들여다볼 수 있게 정렬한다.

해당 로직은 `src/transformers/demangle.ts` 파일에 구현되어 있으며, 난독화된 문자열 프록시 및 접근자 노드를 스키마에 맞게 정형화하는 핵심 메커니즘은 다음과 같다.

```typescript
import { Transformer } from './transformer';
import * as babel from '@babel/core';

export class Demangle extends Transformer {
    /**
     * 프록시 성격의 변수 선언 및 접근자 형태를 식별하여 구조를 정규화한다.
     */
    public static readonly visitor: babel.Visitor = {
        VariableDeclarator(path) {
            const { node } = path;

            // 선언된 변수가 단순 다른 식별자를 참조하는 형태인지 검증
            if (!babel.types.isIdentifier(node.id) || !babel.types.isIdentifier(node.init)) {
                return;
            }

            const originName = node.init.name;
            const binding = path.scope.getBinding(node.id.name);

            // 해당 프록시 변수를 참조하는 모든 지점을 원본 식별자로 강제 매핑
            if (binding && binding.constant) {
                for (const referencePath of binding.referencePaths) {
                    referencePath.replaceWith(babel.types.identifier(originName));
                }
                // 참조 연결이 완료된 불필요한 프록시 선언 노드는 삭제
                path.remove();
            }
        }
    };
}

```

#### 코드 및 동작 메커니즘 분석

* **프록시 참조 변수 식별**: AST를 순회하며 `VariableDeclarator` 노드를 탐색한다. 변수 선언문 중 `var _0x5a1b = _0x12ab;`와 같이 난독화된 핵심 복호화 함수(`_0x12ab`)의 주소값을 단순히 복사하여 시선을 분산시키는 가짜 징검다리 변수 노드를 찾아낸다.
* **참조 경로 역추적 및 일괄 치환**: Babel 스코프 엔진의 `path.scope.getBinding()`을 통해 해당 프록시 변수가 소스코드 내에서 사용된 모든 자취(`referencePaths`)를 실시간으로 추적한다. 이후 추적된 모든 노드를 변조 전 원래의 복호화 식별자명으로 직접 덮어쓴 뒤, 가치가 소멸한 프록시 선언 노드를 트리에서 구조적으로 도려낸다.

이 단계를 통해 복호화 함수를 감싸고 있던 기형적인 별칭(Alias) 체인들이 완전히 제거되어 암호 해독로가 명확하게 개방되며, 파이프라인은 은닉된 텍스트 리터럴을 복원하는 핵심 단계인 StringDecoder 단계로 이어진다.

### Stage 5: StringDecoder

Demangle 단계를 거쳐 은닉되어 있던 복호화 함수의 진입로가 정규화되면, 파이프라인은 역난독화의 가장 핵심인 StringDecoder 단계로 진입한다. 이 단계는 소스코드 내부에서 암호화된 채 숨겨진 문자열들을 추출하여 본래의 텍스트 리터럴로 복원하는 역할을 수행한다.

javascript-obfuscator는 소스코드 내의 모든 문자열을 별도의 배열로 추출하고, 이를 Base64나 RC4 등의 알고리즘으로 암호화하여 숨기는 "Stage 8: StringArray" 단계를 가동한다. StringDecoder 트랜스포머는 바로 이 단계를 무력화한다. 파이프라인 초기 단계(Context Initialization)에서 가상 머신 컨텍스트를 통해 실행 및 캐싱해 두었던 실제 복호화 데이터 매핑 테이블을 기반으로, 코드 곳곳에 산재한 암호문 호출 노드들을 평문 문자열 노드로 강제 치환한다.

해당 로직은 `src/transformers/stringdecoder.ts` 파일에 구현되어 있으며, 복호화 함수 호출을 파싱하여 실제 문자열 리터럴로 치환하는 핵심 메커니즘은 다음과 같다.

```typescript
import { Transformer } from './transformer';
import * as babel from '@babel/core';

export class StringDecoder extends Transformer {
    /**
     * 난독화된 문자열 복호화 함수 호출을 탐색하여 평문 리터럴 노드로 치환한다.
     */
    public static readonly visitor: babel.Visitor = {
        CallExpression(path) {
            const { node } = path;

            // 호출되는 대상이 식별자(Identifier) 형태인지 검증
            if (!babel.types.isIdentifier(node.callee)) {
                return;
            }

            const functionName = node.callee.name;

            // 현재 호출된 함수가 컨텍스트에 등록된 복호화 래퍼 함수인지 확인
            if (!this.context.isStringArrayDecoder(functionName)) {
                return;
            }

            // 가상 머신(VM) 컨텍스트를 이용하여 복호화 함수 실행 및 평문 추출
            const resultValue = this.context.executeDecoder(node);

            if (typeof resultValue === 'string') {
                // 해독된 문자열을 기반으로 새로운 StringLiteral 노드 생성 후 치환
                path.replaceWith(babel.types.stringLiteral(resultValue));
            }
        }
    };
}

```

#### 코드 및 동작 메커니즘 분석

* **복호화 함수 호출 식별**: AST 내에서 함수 호출 형태인 `CallExpression` 노드들을 탐색한다. 호출되는 함수의 이름(`callee.name`)을 추출한 뒤, 해당 식별자가 사전에 분석 컨텍스트가 등록해 둔 문자열 배열 해독용 프록시 함수 스키마와 일치하는지 검증한다.
* **런타임 동적 복호화 및 환원**: 매칭이 확인되면 해당 호출 노드 자체를 가상 머신 환경으로 전달하여 `this.context.executeDecoder(node)`를 통해 실시간으로 디코딩 연산을 수행한다. 해독된 평문 결과물이 안전하게 반환되면, Babel의 `stringLiteral()`을 사용해 원래의 `_0x12ab(0x1f)` 형태의 암호화 호출 구문을 사람이 읽을 수 있는 명확한 문자열 노드로 완전히 덮어쓴다.

이 단계를 거치며 의미를 알 수 없던 수천 개의 복호화 호출문들이 본래의 영문 및 국문 텍스트 리터럴로 복원되며, 파이프라인은 복잡하게 얽힌 제어 흐름을 복구하는 ControlFlow 단계로 이어진다.

### Stage 6: ControlFlow

StringDecoder 단계를 거쳐 숨겨져 있던 모든 문자열이 복원되면, 파이프라인은 난독화의 가장 강력한 방어선 중 하나인 제어 흐름 평탄화를 복구하는 ControlFlow 단계로 진입한다. 이 단계는 거대한 `while-switch` 루프 구조의 상태 머신 안에 가두어 파편화한 코드의 정상적인 실행 순서를 되찾아주는 역할을 수행한다.

javascript-obfuscator는 소스코드의 선형적인 제어 흐름을 무력화하기 위해 실행 순서를 난해하게 쪼개고 이를 런타임 스위치 상태값에 따라 제어하는 "Stage 4: ControlFlowFlattening"을 가동한다. ControlFlow 트랜스포머는 바로 이 단계를  무력화한다. 상태 변수의 변화 추이와 `switch-case` 내부의 분기 조건들을 정적으로 시뮬레이션 및 역추적하여, 본래의 순차적인 선형 실행 블록으로 소스코드를 완벽하게 재조립한다.

해당 로직은 `src/transformers/controlflow.ts` 파일에 구현되어 있으며, 평탄화된 루프 구조를 해체하고 원래의 순서대로 AST 노드를 재배치하는 핵심 메커니즘은 다음과 같다.

```typescript
import { Transformer } from './transformer';
import * as babel from '@babel/core';

export class ControlFlow extends Transformer {
    /**
     * 평탄화 메커니즘이 적용된 SwitchStatement와 루프 노드를 탐색하여 실행 순서를 복구한다.
     */
    public static readonly visitor: babel.Visitor = {
        SwitchStatement(path) {
            const { node } = path;
            
            // 제어 흐름 평탄화 특유의 상태 변수 판별식 구조인지 검증
            if (!babel.types.isIdentifier(node.discriminant)) {
                return;
            }

            const cases = node.cases;
            const executionOrder: babel.types.Statement[] = [];
            
            // 상태 추적 맵을 기반으로 스위치 케이스 블록의 실행 순서를 판별
            const sortedCases = this.determineExecutionOrder(cases);

            for (const caseNode of sortedCases) {
                // 각 케이스 내부의 실행 구문들을 순서대로 수집 (break 문 등은 제외)
                const validStatements = caseNode.consequent.filter(
                    stmt => !babel.types.isBreakStatement(stmt)
                );
                executionOrder.push(...validStatements);
            }

            // switch 문이 감싸고 있던 부모 루프 블록을 원래의 순차적 실행문 배열로 치환
            const parentLoop = path.findParent(p => p.isLoop());
            if (parentLoop) {
                parentLoop.replaceWithMultiple(executionOrder);
            }
        }
    };
}

```

#### 코드 및 동작 메커니즘 분석

* **평탄화 징후 식별**: AST 상에서 제어 흐름의 분기점인 `SwitchStatement` 노드들을 탐색한다. 스위치 문의 판별식(`discriminant`) 패턴을 분석하여 javascript-obfuscator가 주입한 전형적인 런타임 제어용 상태 변수 구조와 일치하는지 검증한다.
* **상태 전이 역추적 및 노드 선형화**: 내부 헬퍼 함수인 `this.determineExecutionOrder()`를 가동하여 난독화 도구가 꼬아놓은 스위치 케이스들의 상태 변수 천이 과정을 정적으로 추적한다. 실제 연산 순서대로 정렬된 케이스 노드에서 의미 있는 실행 구문(`consequent`)들만 필터링해 모은 뒤, 기존에 이를 감싸고 무한 반복시키던 부모 루프 블록 전체를 순차적인 일반 실행문 배열로 강제 치환한다.

이 단계를 통해 복잡한 허브-스포크 형태로 왜곡되어 있던 프로그램의 제어 흐름 그래프(CFG)가 정상적인 선형 구조로 복구되며, 파이프라인은 스코프 내의 참조 배열과 상수를 원래 자리로 되돌리는 ArrayMap & LiteralMap 단계로 이어진다.

### Stage 7: ArrayMap & LiteralMap

제어 흐름이 선형적으로 복구되면, 파이프라인은 스코프 내에 분산되어 있는 고정 배열과 상수 리터럴 변수들을 추적하여 원래의 자리로 환원하는 ArrayMap & LiteralMap 단계로 진입한다. 이 단계는 변수 참조 관계를 복잡하게 만들어 정적 분석을 방해하는 요소를 제거하는 역할을 수행한다.

javascript-obfuscator는 소스코드 내부에서 사용되는 상수를 별도의 고정 배열이나 읽기 전용 맵 변수에 담아두고 참조하도록 변형하는 "Stage 6: Converting" 단계를 수행한다. ArrayMap & LiteralMap 트랜스포머는 이 단계를 무력화한다. 특정 스코프 내에서 고정된 값을 가지는 배열과 리터럴 변수의 바인딩 정보를 정밀하게 추적하여, 해당 변수가 사용된 소스코드 전반의 참조 노드들을 실제 상수 리터럴 값으로 직접 치환(Demap)한다.

해당 로직은 `src/transformers/arraymap.ts` 및 `src/transformers/literalmap.ts` 파일에 구현되어 있으며, 참조 변수를 포착하여 본래의 리터럴 상수로 역매핑하는 핵심 메커니즘은 다음과 같다.

```typescript
import { Transformer } from './transformer';
import * as babel from '@babel/core';

export class ArrayMap extends Transformer {
    /**
     * 상수 배열 선언을 식별하고, 해당 배열을 참조하는 인덱스 노드를 실제 리터럴 값으로 치환한다.
     */
    public static readonly visitor: babel.Visitor = {
        MemberExpression(path) {
            const { node } = path;

            // obj[0]과 같이 대괄호를 이용한 인덱스 접근 형태인지 검증
            if (!babel.types.isIdentifier(node.object) || !babel.types.isNumericLiteral(node.property)) {
                return;
            }

            const arrayName = node.object.name;
            const index = node.property.value;

            // 스코프 내에서 해당 배열 변수의 선언 및 초기화 노드를 역추적
            const binding = path.scope.getBinding(arrayName);
            if (!binding || !babel.types.isVariableDeclarator(binding.path.node)) {
                return;
            }

            const initNode = binding.path.node.init;

            // 선언된 변수가 고정된 ArrayExpression 구조인지 검증
            if (!babel.types.isArrayExpression(initNode)) {
                return;
            }

            const targetElement = initNode.elements[index];

            // 매핑되는 인덱스의 원소가 명확한 리터럴 노드일 경우 일괄 치환 수행
            if (babel.types.isLiteral(targetElement)) {
                path.replaceWith(targetElement);
            }
        }
    };
}

```

#### 코드 및 동작 메커니즘 분석

* **상수 배열 및 인덱스 접근 식별**: AST를 순회하며 객체의 속성이나 배열에 접근하는 `MemberExpression` 노드를 포착한다. 접근 주체가 되는 변수 이름(`arrayName`)과 접근 인덱스 값(`index`)을 추출한 뒤, Babel의 `path.scope.getBinding()`을 호출하여 해당 배열이 선언된 최상위 지점을 역추적한다.
* **컴파일 레벨 데이터 매핑 및 환원**: 추적된 변수 선언문 노드의 초기화 영역(`init`)이 변경 불가능한 고정 배열(`ArrayExpression`) 구조인지 검증한다. 조건을 만족하면 해당 배열 내부의 인덱스에 위치한 원소 노드를 직접 추출하고, 이를 호출부 노드에 강제로 주입하여 `arr[0]` 형태의 참조 구문을 순수한 상수 노드로 완전히 대체한다.

이 단계를 거치며 간접 참조 형태로 분산되어 있던 데이터 흐름이 단일 상수로 통합되며, 파이프라인은 대괄호 형태로 기형화된 객체 접근법을 직관적인 구조로 변환하는 MemberExpressionCleaner 단계로 이어진다.

### Stage 8: MemberExpressionCleaner

간접 참조 구조가 정리되면 파이프라인은 가독성을 높이기 위해 대괄호 표기법으로 왜곡된 객체 속성 접근 방식을 직관적인 점 표기법으로 되돌리는 MemberExpressionCleaner 단계로 진입한다.

javascript-obfuscator는 소스코드 내부의 함수 호출이나 객체 프로퍼티 접근을 가리기 위해 `obj.method()` 형태의 코드를 `obj['method']()`와 같은 문자열 인덱스 접근 방식으로 강제 치환하는 "Stage 5: RenameProperties" 단계를 가동한다. MemberExpressionCleaner 트랜스포머는 이러한 변형 패턴을 타깃으로 삼는다. 대괄호 내부에 박혀 있는 문자열 리터럴을 검사하여 자바스크립트의 표준 식별자 규칙에 부합하는 경우, 이를 점 표기법으로 환원하여 정적 분석 시 코드의 가시성을 확보해 준다.

해당 로직은 `src/transformers/memberexpressioncleaner.ts` 파일에 구현되어 있으며, 기형적인 접근자 노드를 판별하여 안전하게 변환하는 핵심 메커니즘은 다음과 같다.

```typescript
import { Transformer } from './transformer';
import * as babel from '@babel/core';

export class MemberExpressionCleaner extends Transformer {
    // 자바스크립트의 유효한 식별자 이름 명세 (숫자로 시작하지 않는 영문, 숫자, $, _ 조합)
    private static readonly IDENTIFIER_REGEX = /^[a-zA-Z_$][a-zA-Z0-9_$]*$/;

    /**
     * 대괄호 형태의 MemberExpression을 탐색하여 점 표기법으로 변환한다.
     */
    public static readonly visitor: babel.Visitor = {
        MemberExpression(path) {
            const { node } = path;

            // computed가 true이면서 속성명이 명확한 문자열 리터럴인지 검증 (예: obj['prop'])
            if (!node.computed || !babel.types.isStringLiteral(node.property)) {
                return;
            }

            const propertyName = node.property.value;

            // 추출한 문자열이 자바스크립트 문법상 점 표기법(.) 뒤에 붙을 수 있는 명세인지 확인
            if (!MemberExpressionCleaner.IDENTIFIER_REGEX.test(propertyName)) {
                return;
            }

            // 대괄호 접근 형태를 해제하고 순수 식별자(Identifier) 노드로 재조립
            node.property = babel.types.identifier(propertyName);
            node.computed = false; // 점 표기법 체계로 전환
        }
    };
}

```

#### 코드 및 동작 메커니즘 분석

* **대괄호 접근자 및 문자열 검증**: AST를 순회하며 `MemberExpression` 노드를 포착한 뒤, `computed` 프로퍼티가 활성화되어 있는지 확인한다. 이는 배열 인덱싱이나 대괄호 표기법을 쓰고 있음을 의미하므로, 이어서 접근 키가 되는 `property`가 `StringLiteral` 객체인지 체크하여 실제 텍스트 값을 추출한다.
* **정규식 기반 식별자 판별 및 변환**: 추출된 문자열이 `window['eval']`처럼 문법 오류 없이 `window.eval` 형태로 바뀔 수 있는지 자체 정규식 구문(`IDENTIFIER_REGEX`)으로 필터링한다. 조건을 충족하면 내부 문자열을 `babel.types.identifier` 노드로 재포장하고 `computed` 플래그를 비활성화함으로써 문법 구조를 점 표기법으로 즉시 재배치한다.

이 과정을 거치면서 텍스트 전반에 깔려 있던 난해한 문자열 인덱스 호출식들이 직관적인 객체 참조 구조로 세련되게 다듬어지며, 파이프라인은 의미가 소멸한 변수명들을 읽을 수 있는 단어로 일괄 교체하는 마지막 단계인 Rename 단계로 이어진다.

### Stage 9: Rename

모든 구조적 복원과 리터럴 환원이 완료되면, 파이프라인은 마지막 역난독화 과정인 Rename 단계로 진입하여 의미를 상실한 식별자들을 정리한다.

javascript-obfuscator는 소스코드 내부의 전역 변수, 지역 변수, 함수명을 `_0x1a2b` 형태의 난수로 바꾸는 "Stage 7: RenameIdentifiers" 단계를 가동한다. Rename 트랜스포머는 컴파일이 끝난 바이너리에서 원본 변수명을 알아내는 것이 불가능하다는 한계를 극복하기 위해 독특한 방식을 취한다. 의미 없는 난수 식별자들을 그대로 두는 대신, 내장된 수백 개의 영단어 사전(wordList)과 결정론적 난수 생성기를 결합하여 사람이 읽고 서로 구분할 수 있는 고유한 영단어로 변수명을 일괄 교체한다.

해당 로직은 `src/transformers/rename.ts` 파일에 구현되어 있으며, 스코프별 식별자를 추적하여 가독성 높은 단어로 일괄 매핑하는 핵심 메커니즘은 다음과 같다.

```typescript
import { Transformer } from './transformer';
import * as babel from '@babel/core';

export class Rename extends Transformer {
    // 임의의 영단어 조합을 생성하기 위한 내장 사전 데이터
    private wordList: string[] = ['apple', 'ability', 'action', 'actor', 'basic', 'clear'];
    private wordIndex: number = 0;

    /**
     * Scope 정보를 활용하여 난독화된 식별자명을 읽을 수 있는 단어로 재매핑한다.
     */
    public static readonly visitor: babel.Visitor = {
        Identifier(path) {
            const { node } = path;
            const name = node.name;

            // javascript-obfuscator 특유의 _0x로 시작하는 난수 패턴인지 검증
            if (!name.startsWith('_0x')) {
                return;
            }

            // 현재 스코프 내에서 해당 식별자의 바인딩(선언 및 참조 관계)을 추출
            const binding = path.scope.getBinding(name);
            if (!binding) {
                return;
            }

            // 사전에서 중복되지 않는 새로운 단어 할당
            const newName = this.generateUniqueName();

            // 해당 스코프 내에서 대상을 참조하는 모든 노드의 이름을 강제로 변경
            path.scope.rename(name, newName);
        }
    };

    private generateUniqueName(): string {
        const selected = this.wordList[this.wordIndex % this.wordList.length];
        this.wordIndex++;
        return `${selected}_${this.wordIndex}`;
    }
}

```

#### 코드 및 동작 메커니즘 분석

* **난독화 패턴 식별 및 바인딩 추적**: AST를 순회하며 `Identifier` 노드를 발견하면 명칭이 `_0x` 구문으로 시작하는지 필터링한다. 조건이 맞으면 Babel 스코프 가동 엔진을 통해 해당 식별자가 정의된 선언부와 소스코드 내의 모든 참조 지점을 묶어주는 `Binding` 객체를 확보한다.
* **결정론적 단어 재할당 및 스코프 갱신**: 내장된 사전 리스트인 `wordList`와 인덱스 카운팅 기법을 결합하여 고유 명칭(`apple_1`, `ability_2` 등)을 생성한다. 이후 Babel이 지원하는 강력한 리팩토링 API인 `path.scope.rename()`을 실행하여, 해당 변수가 선언되고 사용된 모든 코드 영역의 식별자 체인을 문법적 충돌 없이 안전하게 일괄 변환한다.

이 단계가 완료되면 난수 더미였던 소스코드가 사람이 로직의 흐름을 파악하고 대조해 볼 수 있는 정상적인 텍스트 형태로 정제되며, 변환 파이프라인이 마무리된다.

## 4. Code Generation

역난독화 파이프라인의 최종 단계는 변환 과정을 거쳐 본래의 논리 구조를 회복한 AST를 다시 실행 가능한 자바스크립트 소스코드 문자열로 변환하는 단계다. 수만 개의 객체 노드로 분할되어 메모리에 존재하던 데이터 구조를 인간이 읽을 수 있는 텍스트 파일 형태로 출력하는 역할을 수행한다.

해당 로직은 `src/generator.ts` 파일에 구현되어 있으며, 복원이 완료된 AST를 자바스크립트 소스코드 문자열로 변환하는 핵심 메커니즘은 다음과 같다.

```typescript
import generate, { GeneratorOptions } from '@babel/generator';
import * as babel from '@babel/core';

export class CodeGenerator {
    /**
     * 변환이 완료된 Babel AST를 표준 포맷팅이 적용된 자바스크립트 소스코드로 변환한다.
     * @param {babel.types.File} ast - 복원된 AST 객체
     * @returns {string} 최종 역난독화 소스코드 문자열
     */
    public generateCode(ast: babel.types.File): string {
        const generatorOpts: GeneratorOptions = {
            retainLines: false,
            compact: false,
            minified: false,
            comments: true,
            jsescOption: {
                minimal: true
            }
        };

        // Babel AST를 자바스크립트 텍스트 코드로 변환
        const { code } = generate(ast, generatorOpts);
        return code;
    }
}

```

#### 코드 및 동작 메커니즘 분석

* **가독성 중심의 포맷팅 옵션 설정**: `compact`와 `minified` 옵션을 `false`로 설정하여 난독화 과정에서 누락되었던 들여쓰기와 줄바꿈을 규격에 맞게 재배치한다. 또한 `comments` 옵션을 `true`로 활성화하여 코드 내에 남아 있는 주석들을 유실 없이 결과물에 포함한다.
* **이스케이프 문자열 환원**: `jsescOption` 내의 `minimal` 플래그를 `true`로 활성화한다. 이 옵션은 `\x68\x65\x6c\x6c\x6f` 형태로 변환되어 있던 16진수 및 유니코드 이스케이프 문자열들을 파서의 해석 결과에 따라 원래의 직관적인 평문 문자열(`hello`) 형태로 안전하게 출력하도록 제어한다.

이 단계에서 생성된 텍스트 코드를 파일로 저장함으로써, 수십 개의 보안 레이어로 뒤틀려 있던 javascript-obfuscator 기반 난독화 스크립트에 대한 분석 파이프라인이 완료된다.
