보통의 모니터링 도구들은 User Space에서 Kernel Space의 이벤트를 수집하기 위해 시스템 콜을 호출하거나 디바이스 드라이버를 통해 데이터를 읽어와야 한다. 이 과정에서 커널과 유저 공간을 오가는 **Mode Switch** 오버헤드가 발생하며, 모니터링 데몬이 데이터를 처리하기 위해 CPU 제어권을 넘겨받는 과정에서 무수한 **Context Switching** 비용이 누적되는 문제가 있다. 트래픽이 몰리는 대규모 인프라 환경에서 이는 예측 불가능한 지연 시간을 유발하고 시스템 전체의 성능을 떨어뜨리는 치명적인 원인이 된다.

이런 문제를 해결하고자 eBPF(extended Berkeley Packet Filter)라는 기술이 등장했다. eBPF는 기존 도구들과 달리 무거운 커널 모듈을 직접 올리거나 커널 소스 코드를 수정하지 않고도, **커널 내부에서 안전하게 실행되는 맞춤형 로직을 동적으로 프로그래밍**할 수 있다는 점이 완전히 다르다. 유저 공간으로 모든 데이터를 보내서 처리하는 것이 아니라, 커널 레이어에서 보안상 유의미한 이벤트만 선제적으로 필터링하여 유저 공간으로 전송할 수 있기 때문에 비용을 획기적으로 줄일 수 있고 성능 면에서 훨씬 더 좋다.

이 기술 블로그에서는 eBPF가 무엇인지, 어떻게 동작하는지, 내부 아키텍처와 프로그램 타입, 그리고 실제 생태계 도구들을 언제 어떻게 활용하는지에 대해 전문적이고 깊이 있게 기술하겠다.

# eBPF 동작 원리

eBPF 프로그램은 유저 공간에서 작성된 코드가 커널 내부에서 안전하고 효율적으로 실행되기까지 정교한 라이프사이클을 거친다.

개발자는 먼저 C 또는 Rust 언어를 사용하여 제한된 형태의 eBPF 소스 코드를 작성한다. 일반적인 컴파일러와 달리, eBPF 코드는 **Clang/LLVM 컴파일러**를 통해 특정 CPU 아키텍처(x86, ARM 등)가 아닌 하드웨어 독립적인 가상 머신 명령어 집합인 eBPF 바이트코드(Bytecode)로 변환된다. 이 바이트코드는 8바이트 크기의 구조체 배열로 ELF 오브젝트 파일 형태로 저장된다.

유저 공간의 관리 프로그램(로더)은 이 ELF 파일을 읽어 들인 후, **`bpf()` 시스템 콜**의 `BPF_PROG_LOAD` 명령을 사용하여 바이트코드를 리눅스 커널 내부로 로드한다.

커널에 진입한 바이트코드는 CPU에서 즉시 실행되지 않고, 먼저 Verifier라는 강력한 정적 분석 엔진을 통과해야 한다. Verifier는 프로그램의 모든 실행 경로(Control Flow Graph)를 탐색하며 메모리 오염, 무한 루프, 권한 위반 가능성을 체크하여 커널의 안정성을 완벽히 보장한다.

검증을 통과한 안전한 바이트코드는 커널 내부의 **JIT(Just-In-Time) 컴파일러**로 넘겨진다. JIT 컴파일러는 이 바이트코드를 현재 서버의 실제 호스트 CPU가 직접 이해할 수 있는 네이티브 머신 코드로 즉시 변환한다. 이 단계를 거치기 때문에 eBPF 프로그램은 가상 머신 인터프리터 방식의 오버헤드 없이, 원래 커널에 구현되어 있던 원시 코드(Native Kernel Code)와 동일한 수준의 압도적인 실행 속도로 커널 내부에서 동작하게 된다.

# eBPF 아키텍처

eBPF 아키텍처의 실체는 리눅스 커널 내부에 구현된 하나의 독립적인 **가상 머신(Virtual Machine)** 시스템이다. 단순히 Verifier와 Maps만 존재하는 것이 아니라, 가상 CPU 레지스터 세트, 헬퍼 함수 섭외 인터페이스, 그리고 유저 공간 인터랙션 스택이 유기적으로 맞물려 구동된다.

![Architectur](https://ebpf.io/static/e293240ecccb9d506587571007c36739/f2674/overview.png)

### 가상 머신 레지스터

eBPF 가상 머신은 소프트웨어적으로 에뮬레이션된 11개의 64비트 하드웨어 대동소이 레지스터(`R0` ~ `R10`)를 기반으로 실행된다.

* `R0`은 헬퍼 함수나 eBPF 프로그램 자체의 반환 값(Return Value)을 저장한다.
* `R1`부터 `R5`까지는 커널 내 다른 함수나 헬퍼 함수를 호출할 때 인자(Arguments)를 전달하는 통로로 쓰이며, 프로그램이 시작할 때 `R1`에는 훅 포인트에서 전달된 컨텍스트(Context) 포인터가 자동으로 담긴다.
* `R6`부터 `R9`까지는 피호출자 저장(Callee-saved) 레지스터로, 함수 호출 시에도 값이 보존된다.
* `R10`은 읽기 전용 프레임 포인터(Frame Pointer)로, 512바이트 크기로 할당된 가상 머신 내부의 로컬 스택 메모리 주소를 가리킨다.

### Verifier

Verifier는 eBPF 코드가 전체 시스템을 다운시키거나 패닉에 빠뜨리지 않음을 수학적으로 증명하는 역할을 수행한다.

![Verify](https://ebpf.io/static/7eec5ccd8f6fbaf055256da4910acd5a/fb370/loader.webp)

* **상태 추적(State Tracking):** Verifier는 각 레지스터에 담긴 값의 타입을 `bpf_reg_state` 구조체로 엄격히 추적한다. 레지스터의 값이 단순 상수(SCALAR_VALUE)인지, 컨텍스트 포인터(PTR_TO_CTX)인지, Maps 주소(PTR_TO_MAP_VALUE)인지 실시간으로 대조하며 잘못된 메모리 번지 참조를 물리적으로 차단한다.
* **루프 및 스택 제한:** 커널 스택 오버헤드를 막기 위해 eBPF 프로그램의 로컬 스택은 단 **512바이트**로 엄격히 제한된다. 또한 과거에는 무한 루프 위험 때문에 뒤로 점프하는 명령어(Backward Jump)가 전면 금지되었으나, 최신 커널에서는 제한된 범위 내에서 유한성이 증명되는 루프(Bounded Loops)에 한해 허용된다.
* **헬퍼 함수 유효성 검사:** eBPF 프로그램이 커널 기능을 안전하게 쓰도록 허용된 API인 헬퍼 함수(Helper Functions)를 호출할 때, 인자로 전달되는 레지스터들의 상태와 타입이 해당 함수의 프로토타입(`bpf_func_proto`) 규격에 부합하는지 정적으로 검증한다.

### eBPF Maps

eBPF 프로그램은 이벤트가 발생했을 때 실행되고 바로 종료되는 Run-to-Completion 방식으로 동작하므로 상태를 내부에 저장할 수 없다. 따라서 연속적인 이벤트 간에 상태를 유지하거나, 유저 공간의 애플리케이션과 데이터를 주고받기 위해 eBPF Maps이라는 커널 내 공유 메모리 데이터 구조를 사용한다.

![eBPF Maps](https://ebpf.io/static/e7909dc59d2b139b77f901fce04f60a1/f8644/map-architecture.webp)

유저 공간은 `bpf(BPF_MAP_CREATE, ...)` 시스템 콜을 통해 Maps을 생성하고 파일 디스크립터(FD)를 획득하여 제어하며, 커널 내 eBPF 프로그램은 고성능 내장 API인 헬퍼 함수(`bpf_map_lookup_elem`, `bpf_map_update_elem`)를 써서 Maps에 직접 접근한다. key-value 형태로 관리되는 Maps의 주요 타입은 다음과 같다.

* **`BPF_MAP_TYPE_HASH` / `BPF_MAP_TYPE_ARRAY`:** 가장 널리 쓰이는 기본 저장소다. 해시 Maps은 프로세스 정보나 IP 주소 같은 임의의 구조체를 키로 삼아 동적 상태를 관리할 때 쓰이고, 어레이 Maps은 4바이트 정수 인덱스를 사용하여 고속 조회가 필요한 설정값을 저장할 때 쓰인다.
* **`BPF_MAP_TYPE_PERF_EVENT_ARRAY` & `BPF_MAP_TYPE_RINGBUF`:** 대량의 이벤트를 유저 공간으로 스트리밍할 때 쓰이는 버퍼 구조다. 과거의 Perf Buffer는 CPU 코어별로 독립된 버퍼를 두어 경합을 피했으나, 특정 코어에 트래픽이 몰릴 때 버퍼가 넘쳐 데이터가 유실되는 한계가 있었다. 이를 개선한 링 버퍼(Ring Buffer)는 모든 코어가 하나의 거대한 메모리 영역을 공유하되 락리스(Lockless) 메커니즘을 적용하여 메모리 효율성을 극대화하고 데이터 유실을 없앴다.
* **`BPF_MAP_TYPE_PROG_ARRAY`:** eBPF 프로그램 안에서 또 다른 eBPF 프로그램으로 실행 문맥을 완전히 넘겨주는 테일 콜(Tail Call)을 구현할 때 사용된다. 단일 프로그램의 복잡도나 Verifier 명령어 수 제한을 우회하기 위해 다단계 필터링 구조를 짤 때 핵심 역할을 한다.

### 헬퍼 함수

eBPF 가상 머신 내부에서 커널 공간의 일반 함수를 제약 없이 직접 호출하는 것은 메모리 변조 위험으로 인해 전면 금지된다. 대신 커널은 안전성이 검증된 함수들의 화이트리스트인 **헬퍼 함수** 인터페이스를 제공한다. eBPF 프로그램은 이 헬퍼 함수들을 경유해서만 시스템 시간을 조회하거나(`bpf_ktime_get_ns`), Maps 데이터를 조작하고, 패킷을 변경하거나, 프로세스 정보에 접근할 수 있다.

# 프로그램 타입

eBPF 프로그램은 커널 내부 어디에나 배치될 수 있는 게 아니다. 사전에 정의된 프로그램 타입에 따라 진입할 수 있는 후킹 포인트와 접근 가능한 Context가 철저하게 격리되고 제한된다.

![Hook](https://ebpf.io/static/b4f7d64d4d04806a1de60126926d5f3a/ef3e7/syscall-hook.webp)

### 추적 및 관측 (Tracing)

* **Kprobes (Kernel Probes) & Kretprobes:** 커널 내부 대부분의 함수 진입점(Entry)과 반환점(Exit)에 동적으로 설치할 수 있는 후킹 포인트다. 소스 코드를 전혀 고치지 않고 특정 시스템 콜(`sys_execve` 등)이나 내부 서브시스템 동작을 정밀 추적할 수 있어 깊이 있는 분석에 유용하다. 다만 커널 버전이 올라가며 함수 이름이나 시그니처가 바뀌면 코드가 오동작할 수 있는 커널 의존성 리스크가 존재한다.
* **Tracepoints:** 커널 개발자들이 소스 코드 내에 명시적으로 매립해 둔 정적 후킹 포인트다(예: `sched_process_exec`). 추적 데이터의 구조가 안정적인 API 인터페이스 형태로 보장되므로, 커널 버전이 바뀌어도 유지보수가 용이하다는 강력한 장점이 있다.
* **LSM (Linux Security Module) BPF:** 커널 5.7부터 도입된 타입으로, 기존의 정적 보안 모듈(AppArmor, SELinux)이 권한 검사를 하던 LSM 커널 훅에 eBPF 코드를 직접 결합한다. 단순히 이벤트를 관측하는 것을 넘어, eBPF 프로그램이 반환하는 값(EPERM 등 에러 코드)을 통해 커널이 해당 시스템 콜 수행을 물리적으로 거부(Deny)하도록 강제하는 실시간 방어 처리를 구현할 수 "있다.

### 네트워크 (Networking)

* **XDP (eXpress Data Path):** 리눅스 네트워크 스택의 최하단, 즉 네트워크 디바이스 드라이버가 패킷을 수신하는 가장 첫 번째 단계 레이어에서 패킷을 가로챈다. 무거운 커널 메모리 구조체인 `sk_buff` 레이어로 변환되기 전 원시 바이트 상태에서 처리하기 때문에, 초고속 패킷 드롭(DDoS 방어)이나 고성능 로드 밸런싱을 구사할 수 있으며 지원되는 하드웨어 칩셋에 코드를 직접 오프로드(Offloading)하는 것도 가능하다.
* **TC (Traffic Control):** XDP보다 한 단계 위인 Ingress 및 Egress 단에서 패킷 분류 및 트래픽 제어를 수행한다. `sk_buff` 구조체에 온전히 접근할 수 있어 L3/L4 레이어 정보 및 소켓 메타데이터를 가공하기 수월하며, 컨테이너 환경의 가상 이더넷 인터페이스(`veth`)와 결합하여 고성능 컨테이너 네트워킹 라우팅 엔진을 구성하는 기반이 된다.

# eBPF 생태계

eBPF의 막강한 기능을 쓰기 위해 모든 로직을 바닥부터 C 코드로 작성하고 Verifier 규칙을 맞추는 것은 대단히 난이도가 높고 비효율적이다. 인프라 환경에서는 이미 성능과 안정성이 검증된 완제품 형태의 오픈소스 도구들을 활용하며, 인프라의 요구사항에 맞춰 도구를 적절히 결합해 운영하는 것이 일반적이다. 대표적인 소프트웨어로는 Falco, Tetragon, Cilium이 있다.

### Falco (보안 및 동작 탐지)

시스템 콜 수준(`sys_enter`, `sys_exit`)의 추적에 최적화된 위협 탐지 도구다. 리눅스 시스템 콜 이벤트를 고속으로 수집하고, 사전에 정의된 규칙(Rule) 엔진과 대조하여 이상 징후를 찾아낸다. 대량의 시스템 이벤트를 유실 없이 수집하고 분석하는 성능이 매우 뛰어나며, 이미 시장에 잘 정의된 위협 탐지 규칙 세트(Sigma 라이브러리 등)가 많아 인프라 전반의 비정상 행위를 모니터링하고 사후 감사 로그를 남길 때 사용하기 가장 좋다.

### Tetragon (실시간 보안 및 인라인 차단)

Falco가 시스템 콜 입구에서 주로 비동기 탐지를 수행한다면, Tetragon은 커널 내부 깊숙한 핵심 함수 수준(`fd_install` 등)을 정밀 타격하여 동적으로 후킹하는 도구다.
단순히 이상 행위를 모니터링하는 데 그치지 않고, 정책 위반 감지 즉시 커널 내부에서 `bpf_send_signal()`을 호출하여 해당 프로세스에 `SIGKILL`을 날리는 **실시간 동기식 차단** 능력을 제공한다. 또한 커널 내부에서 프로세스의 부모-자식 계보(Lineage) 정보를 완벽히 유지하기 때문에, 위협 인자 값을 검증하는 시점과 실제 실행하는 시점 사이의 타이밍 차이를 노리는 고도화된 우회 공격(TOCTOU 구조적 취약점)을 원천 차단해야 하는 고보안 환경에서 반드시 사용해야 하는 도구다.

### Cilium / Hubble (고성능 네트워킹 및 관측성)

쿠버네티스(Kubernetes) 환경에서 네트워크를 담당하는 CNI(Container Network Interface) 도구다. 전통적인 리눅스 방화벽인 `iptables`는 규칙이 늘어날수록 모든 규칙을 순차 탐색($O(n)$)해야 하므로 파드 개수가 많아지면 패킷 처리 속도가 무참히 떨어지지만, Cilium은 eBPF 해시 Maps 구조를 기반으로 목적지를 단번에 찾아내어($O(1)$) 라우팅 효율을 극대화한다. 서비스 메쉬(Service Mesh) 환경에서 무거운 프록시(Envoy sidecar) 오버헤드 없이 L3/L4/L7 네트워크 패킷을 초고속으로 제어하고, Hubble을 통해 네트워크 흐름을 시각적으로 관측하고 싶을 때 채택한다.

### 언제 어떤 것을 사용하는 게 좋은가?

결론적으로 최신 클라우드 네이티브 아키텍처를 결함 없이 설계하려면 이 도구들을 계층적으로 공존시켜야 한다.

쿠버네티스 인프라 전체의 **사이드카 없는 고성능 네트워킹 및 서비스 메쉬 가시성**을 밑바탕에 깔기 위해 **Cilium**을 기본 CNI로 전면 채택하고, 그 위에서 컨테이너 내부의 비정상적인 실행 경로를 실시간으로 추적하고 우회 공격을 원천 봉쇄함과 동시에 즉각적인 무력화(Kill) 조치를 취해야 하는 **인라인 실시간 방어 영역에는 Tetragon**을 결합하여 가동하는 아키텍처가 가장 이상적이다.
