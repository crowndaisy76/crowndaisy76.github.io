Linux 및 UNIX 환경에서는 시스템의 보안 상태를 점검하고 취약점을 파악하기 위해 다양한 진단 도구를 활용한다. 본 글에서는 별도의 에이전트 설치 없이 순수 셸 스크립트 기반으로 동작하여, 시스템 보안 감사(Security Auditing)와 하드닝(Hardening)을 수행하는 오픈소스 도구인 Lynis의 내부 아키텍처와 작동 원리를 분석하고자 한다.

# Lynis 분석

Lynis는 Linux, macOS, BSD 등 유닉스 기반 시스템을 위한 보안 감사 도구이다. 시스템에 직접 에이전트를 설치할 필요가 없는 구조로 이루어져 있으며, 시스템 자체에서 심층적인 보안 스캔을 실행하여 방어 체계를 점검하고 시스템 구성을 강화하기 위한 지침을 제공한다. 컴플라이언스 테스트, 취약점 탐지, 소프트웨어 패치 관리 등 다양한 목적으로 시스템 관리자 및 보안 전문가에 의해 활용된다.

Lynis의 전체적인 진단 및 감사 프로세스는 크게 세 가지 단계로 구성된다.

1. **Initialization**: 검사를 수행하기 전, 시스템 점검 기준이 정의된 프로파일과 설정 파일을 로드한다. 이 단계에서 권장되는 커널 설정, 주요 시스템 파일의 권한 등 감사에 필요한 초기 지침을 파악하고 스캔을 준비한다.

2. **Discovery**: 현재 시스템의 운영체제 종류를 식별하고, 시스템 내부에 설치된 기본 명령어 및 바이너리 도구들의 위치를 파악한다. 셸 스크립트 기반 도구의 특성상 시스템에 내장된 유틸리티를 활용하여 점검을 수행해야 하므로, 스캔에 활용할 수 있는 명령어 환경을 사전에 탐색하여 구성한다.

3. **Auditing**: 파악된 시스템 환경을 바탕으로 모듈화된 개별 테스트 및 플러그인을 실행한다. 네트워크, 파일 시스템, 사용자 권한 등 다양한 범주에 걸쳐 실제 시스템의 현재 설정 값을 권장 기준과 대조하는 본격적인 감사를 수행한다. 검사가 완료되면 식별된 취약점과 보안을 강화하기 위한 하드닝 조언 및 경고 사항을 최종 결과로 반환한다.

## 1. Initialization

Lynis의 초기화(Initialization) 단계는 본격적인 시스템 검사에 앞서 보안 감사의 기준이 되는 지침을 파악하고 점검 환경을 구성하는 과정이다. 이 단계에서 가장 핵심적으로 활용되는 아티팩트는 `.prf` 확장자를 가지는 프로파일(Profile) 파일이다.

프로파일 파일을 이용하는 이유는 시스템마다 요구되는 보안 수준과 컴플라이언스(PCI-DSS, ISO27001, HIPAA 등) 기준이 다르기 때문이다. 셸 스크립트 소스코드를 직접 수정하지 않고도, 관리자가 프로파일의 설정값을 변경하여 검사 항목을 유연하게 조정하거나 필요한 모듈만 선별적으로 활성화할 수 있도록 설계되어 있다. 기본적으로 `default.prf` 파일이 점검 기준으로 로드되며, 사용자 정의 설정을 위해 `custom.prf` 등을 동일한 디렉토리에 배치하여 덮어씌우는 방식으로 활용된다.

초기화 단계에서 `include/profiles` 스크립트가 실행되며 프로파일 파일 내부의 데이터를 파싱한다. 프로파일 아티팩트 내부는 크게 전역 설정 및 플러그인, 커널 파라미터 기준, 파일 권한 점검 기준으로 구성되어 있다.

먼저, 전역 설정 및 플러그인 항목에서는 전반적인 스캔 모드(light, normal, full)와 검사에 포함할 대상 플러그인 목록을 정의한다. 

```ini
# default.prf
# ... 생략 ...
test-scan-mode=full            # 스캔 모드 깊이 설정
# ... 생략 ...
plugin=authentication          # 인증 관련 플러그인 활성화
plugin=crypto                  # 암호화 관련 플러그인 활성화
plugin=file-systems            # 파일 시스템 관련 플러그인 활성화
# ... 생략 ...
```

또한, 시스템 하드닝의 핵심 지표가 되는 커널 설정(sysctl)의 권장값을 정의한다. `config-data` 지시자를 통해 운영체제의 커널 파라미터가 가져야 할 기댓값과, 설정이 일치할 경우 부여할 보안 점수(Hardening Points)를 명시한다. 이를 통해 이후 진행될 감사 단계에서 현재 시스템에 적용된 커널 값과 프로파일의 권장값을 대조할 수 있는 기준점을 세운다.

```ini
# default.prf
# ... 생략 ...
# config-data=sysctl;[설정키];[기댓값];[보안점수];[설명];[확인명령어];[해결책필드];
config-data=sysctl;kernel.randomize_va_space;2;1;Randomize of memory address locations (ASLR);sysctl -a;url:https;//kernel.org/doc/Documentation/sysctl/kernel.txt;category:security;
config-data=sysctl;kernel.sysrq;0;1;Disable magic SysRQ;sysctl -a;url:https;//kernel.org/doc/Documentation/sysctl/kernel.txt;category:security;
# ... 생략 ...
```

시스템 내 주요 파일 및 디렉토리의 권한 상태를 검증하기 위한 데이터도 이 아티팩트에 포함되어 있다. `permfile`과 `permdir` 지시자를 사용하여 특정 파일의 허용된 소유자, 그룹, 그리고 파일 권한(읽기/쓰기/실행)을 정의한다. 정의된 보안 기준을 벗어나는 파일이 발견될 경우 출력할 조치 수준(WARN 또는 NOTICE)을 명시한다.

```ini
# default.prf
# ... 생략 ...
# permfile=[파일경로]:[권한]:[소유자]:[그룹]:[액션]:
permfile=/etc/passwd:rw-r--r--:root:-:WARN:
permfile=/etc/ssh/sshd_config:rw-------:root:-:WARN:

# permdir=[디렉토리경로]:[권한]:[소유자]:[그룹]:[액션]:
permdir=/root/.ssh:rwx------:root:-:WARN:
# ... 생략 ...
```

결과적으로 Initialization 단계는 `include/profiles` 로직을 통해 `default.prf`와 같은 프로파일 아티팩트를 파싱하여, 시스템 검사에 필요한 모든 기준 값을 스크립트 내부 변수로 할당하는 과정이다. 분석 엔진은 대상 시스템을 어떤 기준으로 검사하고 평가할지에 대한 지침을 이 아티팩트로부터 확보한 뒤, 다음 단계인 Discovery으로 넘어가게 된다.

## 2. Discovery

환경 탐색(Discovery) 단계는 정의된 보안 감사 기준을 적용하기 전, 대상 시스템의 운영체제 환경과 스캔에 사용할 명령어 자원들의 상태를 파악하는 과정이다. 이 단계에서 가장 핵심적으로 검사하고 수집하는 대상은 시스템 내에 존재하는 '바이너리 실행 파일의 경로 목록'과 '운영체제 식별 파일 내의 메타데이터'이다.

셸 스크립트 기반 감사 도구는 자체적인 독립 탐지 바이너리를 내장하지 않으므로, 시스템에 설치된 기본 유틸리티에 의존하여 정보를 수집해야 한다. 따라서 어떤 유틸리티가 사용 가능한지 식별하고 해당 바이너리의 경로를 명확히 확보하는 것이 분석의 무결성을 담보하는 요건이 된다.

### 운영체제 및 배포판 식별 데이터 수집

정확한 보안 감사 기준을 적용하기 위해서는 현재 구동 중인 운영체제와 배포판의 종류를 식별해야 한다. 이를 위해 검사 엔진은 리눅스 및 유닉스 표준 아티팩트 경로를 순회하며 메타데이터를 수집한다.

주요 수집 대상 아티팩트는 `/etc/os-release`, `/etc/redhat-release`, `/etc/debian_version` 등 배포판 식별 파일들과 `uname` 명령어의 실행 결과이다. 소스코드 내부에서는 시스템 검증 로직을 거쳐 해당 아티팩트들로부터 운영체제 이름, 버전 정보를 추출하여 전역 변수인 `OS`, `OS_NAME`, `OS_VERSION`, `OS_FULLNAME`에 할당한다.

```bash
# include/osdetection 내의 실제 커널 및 배포판 식별 데이터 처리 로직

case $(uname) in
    Linux)
        OS="Linux"
        OS_NAME="Linux"
        
        # os-release 아티팩트 스캔 및 내부 메타데이터 파싱
        if [ -r /etc/os-release ]; then
            . /etc/os-release
            OS_NAME="${NAME}"
            OS_VERSION="${VERSION_ID}"
            OS_FULLNAME="${NAME} ${VERSION_ID}"
            
        # redhat-release 아티팩트 스캔 및 데이터 수집
        elif [ -r /etc/redhat-release ]; then
            OS_NAME="Red Hat"
            OS_VERSION=$(cat /etc/redhat-release | head -n 1)
            
        # debian_version 아티팩트 스캔 및 데이터 수집
        elif [ -r /etc/debian_version ]; then
            OS_NAME="Debian"
            OS_VERSION=$(cat /etc/debian_version | head -n 1)
        fi
    ;;
esac

```

### 바이너리 실행 파일의 경로 식별 및 유효성 검증

보안 감사를 진행하는 동안 데이터 파싱과 상태 조회에 사용될 필수 명령어들의 유효성을 확보하기 위해 시스템 내 바이너리 아티팩트들의 경로를 식별한다.

이 과정에서 툴은 외부 명령어나 특정 함수에 의존하지 않고, 시스템 환경 변수인 `${PATH}` 경로를 기반으로 직접 파일 시스템 스캔을 수행한다. `PATH`에 등록된 디렉토리 목록을 추출한 뒤, `ls -p` 명령어를 통해 각 디렉토리 내부의 파일 목록을 순회한다. 순회 과정에서 `case` 조건문을 사용해 파일명을 대조하고, 일치하는 파일이 발견되면 해당 바이너리의 절대 경로를 `AWKBINARY`, `GREPBINARY`, `SEDBINARY`, `PSBINARY`, `SSBINARY` 등의 전역 변수에 할당한다.

또한 파일 검사 시 `-u`(SetUID)와 `-g`(SetGID) 옵션을 사용해 특권 권한이 부여된 바이너리를 식별하고 개수를 기록한다.

```bash
# include/binaries 내의 실제 바이너리 디렉토리 스캔 및 환경 변수 매핑 로직

# PATH 변수의 디렉토리 경로를 파싱하여 순회 구문 실행
for SCANDIR in ${BIN_PATHS}; do
    SCANDIR=$(echo "${SCANDIR}" | sed 's/!!space!!/ /g')
    
    if [ -d "${SCANDIR}" ]; then
        # 디렉토리 내 파일 목록 추출 (하위 디렉토리 제외)
        FIND=$(ls -p "${SCANDIR}" | grep -v '/$')
        
        for FILENAME in ${FIND}; do
            BINARY="${SCANDIR}/${FILENAME}"
            
            # 특권 권한(SetUID, SetGID) 파일 검증 및 자원 기록
            if [ -u "${BINARY}" ]; then
                NSUID_BINARIES=$((NSUID_BINARIES + 1))
                SUID_BINARIES="${SUID_BINARIES}${BINARY} "
            fi
            if [ -g "${BINARY}" ]; then
                NSGID_BINARIES=$((NSGID_BINARIES + 1))
                SGID_BINARIES="${SGID_BINARIES}${BINARY} "
            fi
            
            # 파일명 매칭을 통한 변수 할당 처리
            case ${FILENAME} in
                awk)       AWKBINARY=${BINARY};;
                grep)      GREPBINARY=${BINARY};;
                sed)       SEDBINARY=${BINARY};;
                ps)        PSBINARY=${BINARY};;
                ss)        SSBINARY=${BINARY};;
                netstat)   NETSTATBINARY=${BINARY};;
                find)      FINDBINARY=${BINARY};;
            esac
        done
    fi
done

# 감사 진행에 필요한 최소 필수 도구의 존재 여부 최종 검증
[ "${AWKBINARY:-}" ] || ExitFatal "awk binary not found"
[ "${CAT_BINARY:-}" ] || ExitFatal "cat binary not found"
[ "${FINDBINARY:-}" ] || ExitFatal "find binary not found"
[ "${GREPBINARY:-}" ] || ExitFatal "grep binary not found"
[ "${PSBINARY:-}" ] || ExitFatal "ps binary not found"
[ "${SEDBINARY:-}" ] || ExitFatal "sed binary not found"

```

이렇게 탐색된 명령어들의 경로 정보는 변수에 상수로 고정된다. 이후 3단계인 Auditing에서 시스템 설정 파일을 분석하거나 네트워크 연결 상태를 조회할 때 이 식별된 바이너리 아티팩트들만을 호출하여 검사를 수행하게 된다.

결과적으로 Discovery 단계는 환경 내의 가상 파일 시스템 메타데이터와 명령어 바이너리 아티팩트의 위치를 조사하여, 셸 스크립트가 시스템 정보를 추출할 수 있도록 실행 자원 맵을 구성하는 과정이다.


## 3. Auditing

보안 감사(Auditing) 단계는 이전 과정에서 식별된 시스템 명령어 자원과 전처리된 기준 데이터를 활용하여 실제 엔드포인트의 취약점과 설정 오류를 전수 조사하는 핵심 과정이다. 검사 엔진은 가상 파일 시스템의 커널 파라미터 상태 기록, 사용자 계정 설정 파일, 네트워크 포트 바인딩 정보 등의 아티팩트를 직접 참조하여 실시간 위협 기법을 사냥한다.

내부 로직은 모듈화된 독립 점검 파일들을 순차적으로 호출하며, 각 도메인 영역별로 다음과 같은 핵심 아티팩트의 세부 필드를 검사한다.

### 프로세스 및 메모리 은닉 위협 탐지 (`include/tests_memory_processes`)

시스템 정보 수집 명령어의 결과와 운영체제 내부 커널 가상 파일 시스템의 불일치를 비교하여 프로세스 은닉형 백도어나 루트킷의 존재 여부를 탐지한다.

* **/proc/meminfo:** 내부의 메모리 할당량 데이터를 조회하여 시스템의 총 물리 메모리 크기를 식별하고 이를 환경 변수에 기록한다.

```bash
# 실제 include/tests_memory_processes 내 파싱 코드
if [ -f ${ROOTDIR}proc/meminfo ]; then
    LogText "Result: found ${ROOTDIR}proc/meminfo"
    Display --indent 2 --text "- Checking ${ROOTDIR}proc/meminfo" --result "${STATUS_FOUND}" --color GREEN
    FIND=$(${AWKBINARY} '/^MemTotal/ { print $2, $3 }' ${ROOTDIR}proc/meminfo)
    MEMORY_SIZE=$(echo ${FIND} | ${AWKBINARY} '{ print $1 }')

```

### 계정 및 인증 권한 감사 (`include/tests_authentication`)

권한 상승 공격 및 계정 탈취 위협을 식별하기 위해 사용자 데이터베이스와 패스워드 섀도 파일의 무결성을 검증한다.

* **/etc/passwd:** 계정 정보 파일 내 세 번째 필드인 UID 값을 조회하여, 최고 권한을 의미하는 UID `0` 계정이 표준 관리자 계정인 root 외에 추가로 가공되어 상주하는지 전수 검사한다.

```bash
# 실제 include/tests_authentication 내 UID 0 검사 코드
if [ ${SKIPTEST} -eq 0 ]; then
    LogText "Test: Checking for accounts with UID 0"
    FOUND_ACCOUNTS=$(${AWKBINARY} -F: '$3 == 0 { print $1 }' ${ROOTDIR}etc/passwd)

```

### 로그 상태 및 흔적 삭제 행위 감사 (`include/tests_logging`)

* **lsof 결과 기반 활성 로그 파일 목록:** 프로세스가 참조하고 있는 파일 플래그 정보 중 파일의 형태 속성이 일반 파일(`REG`)이고 파일 크기가 `0` 바이트이면서 확장자가 `log`로 끝나는 스트림 데이터를 추출하여, 흔적을 지우기 위한 의도적 초기화 행위가 발생했는지 확인한다.
