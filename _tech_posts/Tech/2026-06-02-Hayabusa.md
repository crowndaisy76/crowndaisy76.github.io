현대 침해사고 대응 및 위협 헌팅 과정에서 분석가는 대상 시스템의 변경을 최소화하고 신속하게 침해 지표(IOC)를 식별해야 한다. 본 보고서에서는 이러한 비침습적 분석 환경에서 Windows 이벤트 로그(.evtx)를 타겟으로 삼아 초고속으로 위협을 탐지하는 오픈소스 엔진, Hayabusa의 구체적인 구동 원리와 코드 체계를 분석하고 정리하고자 한다.

# Hayabusa 분석
Hayabusa는 Rust 언어로 구현된 Windows 이벤트 로그 고속 분석 도구이다. 기본 Windows 이벤트 뷰어를 활용한 그래픽 사용자 인터페이스(GUI) 기반 분석은 대용량 로그 데이터를 처리할 때 파싱 속도가 저하되는 한계가 있다. Hayabusa는 Rust의 병렬 처리 기술과 파일 전처리 필터링 알고리즘을 적용하여 탐지 속도를 단축한다.

Hayabusa의 데이터 처리 및 위협 탐지 프로세스는 크게 세 가지 단계로 구성된다.

1. **Preprocessing**: 스캔을 시작하기 전, 입력된 이벤트 로그 파일들의 초기 레코드를 확인하여 내부에 실제 존재하는 이벤트 채널 목록을 식별한다. 이를 기반으로 분석 대상 파일에 존재하지 않는 채널을 타겟으로 하는 Sigma Rule들을 파싱 및 규칙 로드 대상에서 제외한다. 이 채널 기반 상호 배제 필터링을 통해 불필요한 규칙 로딩에 소요되는 메모리와 CPU 자원을 절약한다.

2. **Detection**: 규칙 조건 대조 시 연산 비용이 높은 정규표현식의 사용을 최소화한다. 메모리에 로드된 규칙과 로그 데이터를 비교할 때, 규칙 내 텍스트 패턴을 Rust 문자열 라이브러리의 표준 내장 메서드인 전방 일치, 후방 일치, 부분 일치 연산으로 변환하여 문자열 대조를 수행한다.

3. **Normalization & Enrichment**: 서로 다른 이벤트 로그 원본의 필드명을 식별하기 쉬운 타임라인 표준 명칭으로 통합하는 정규화를 수행한다. 로그 내에 IP 주소가 포함되어 있을 경우 외부 데이터베이스와 연동하여 자율시스템번호(ASN), 국가 코드 등의 외부 식별 정보를 결합하여 확장한 뒤 최종 타임라인 결과를 반환한다.

## 1. Preprocessing

Hayabusa의 전처리 단계는 대용량 로그 분석 시 발생하는 불필요한 연산을 사전에 차단하는 핵심 최적화 과정이다. 분석 엔진이 모든 파일과 탐지 규칙을 무작정 메모리에 올리는 대신, 입력된 로그 데이터의 특성을 미리 파악하여 분석에 필요한 요소들만 선별적으로 로드한다. 관련된 핵심 로직은 `src/filter.rs` 파일에 구현되어 있다.

이 과정을 이해하기 위해서는 먼저 Hayabusa가 처리하는 Windows 이벤트 로그의 내부 구조를 살펴볼 필요가 있다. Hayabusa가 `.evtx` 파일을 파싱하면 각 로그 레코드는 내부적으로 아래와 같은 JSON 형태로 변환된다.

```json
{
  "Event": {
    "System": {
      "Provider_attributes": { "Name": "Microsoft-Windows-Sysmon" },
      "EventID": 1,
      "Channel": "Microsoft-Windows-Sysmon/Operational"
      // ... 생략 ...
    },
    "EventData": {
      "CommandLine": "C:\\Windows\\System32\\cmd.exe"
      // ... 생략 ...
    }
  }
}
```

위 구조에서 볼 수 있듯, 모든 이벤트 로그는 `Event` 객체 하위에 메타데이터를 담은 `System`과 실제 상세 행위가 기록된 `EventData`를 포함한다. 전처리 단계에서 Hayabusa가 가장 주목하는 값은 `Event.System.Channel` 경로에 위치한 채널 정보(예: `Security`, `System`, `Microsoft-Windows-Sysmon/Operational` 등)이다. 

분석 대상인 EVTX 파일을 처리할 때, 파일 전체를 파싱하는 오버헤드를 피하기 위해 `peek_channel_from_evtx_first_record` 함수를 사용한다. 이 함수는 수 기가바이트의 파일이라도 맨 처음에 위치한 단 하나의 레코드만을 읽어 들여 위 예시의 `Channel` 값을 추출한다. 확인된 채널 정보는 파일 경로와 함께 해시맵(HashMap) 형태로 매핑된다.

```rust
// src/filter.rs
fn peek_channel_from_evtx_first_record(...) -> HashMap<String, Vec<PathBuf>> {
    // ... 생략 ...
    let mut records = parser.records_json_value();
    match records.next() { // 파일 전체가 아닌 첫 번째 레코드만 파싱하여 확인
        Some(Ok(rec)) => {
            let key = rec.data["Event"]["System"]["Channel"] // 채널 정보 추출
            // ... 생략 ...
        }
    }
    // ... 생략 ...
}
```

로그 파일의 특성을 파악한 후에는 `extract_channel_from_rules` 함수를 통해 메모리에 적재할 Sigma Rule들을 검사한다. 규칙이 작성된 YAML 구조를 탐색하여 특정 채널을 타겟으로 하는지 확인하고, 앞서 첫 번째 레코드에서 추출한 EVTX 파일의 실제 채널 목록과 교집합을 찾는다. 만약 분석 대상 로그에 없는 채널을 요구하는 규칙이라면 매칭될 가능성이 없으므로, 메모리 로드 대상에서 완전히 배제된다.

마지막으로 `create_channel_filter` 함수는 위의 정보들을 종합하여 탐지 엔진에 적용할 최종 필터 객체인 `ChannelFilter`를 생성한다. 이 구조체는 교집합 대조를 통과한 유효한 규칙과 로그 파일 목록만을 포함한다. 결과적으로 메인 분석 엔진은 이 필터를 거친 데이터만 처리하게 되며, 시스템 자원 소모를 최소화하면서도 탐지 속도를 극대화할 수 있다.

```rust
// src/filter.rs
pub fn create_channel_filter(...) -> ChannelFilter {
    // ... 생략 ...
    let (x, y) = extract_channel_from_rules(rule_nodes, &channels.keys().cloned().collect());
        
    ChannelFilter {
        rulepathes: x,                  // 대조를 통과하여 실제로 로드할 규칙 경로
        intersec_channels: y.into_iter().collect(), 
        evtx_channels_map: channels,    
    }
    // ... 생략 ...
}
```

## 2. Detection

전처리 단계를 통과하여 메모리에 로드된 규칙과 이벤트 로그 데이터를 본격적으로 대조하는 탐지 단계이다. 대용량 로그의 수많은 필드 값을 검사할 때 정규표현식을 남용하면 연산 비용이 급증하여 스캔 속도가 저하된다. Hayabusa는 이를 방지하기 위해 규칙 내의 텍스트 패턴을 분석하여, 가능한 경우 정규표현식 대신 Rust의 표준 문자열 메서드를 활용하는 고속 매칭(Fast Match) 알고리즘을 적용한다. 이 핵심 로직은 `src/detections/rule/fast_match.rs` 파일에 구현되어 있다.

이해를 돕기 위해 Sigma Rule에서 프로세스 실행을 탐지하는 패턴을 예로 들 수 있다. 규칙의 탐지 조건이 다음과 같이 정의되어 있다고 가정해 본다.

```yaml
// Sigma Rule 탐지 조건 예시
detection:
  selection:
    EventID: 1
    Image: '*\cmd.exe'
  condition: selection
```

위 규칙에서 `Image` 필드의 값인 `*\cmd.exe`는 앞부분에 와일드카드(`*`)를 포함하고 있다. 일반적인 분석 도구는 이를 처리하기 위해 정규표현식 엔진을 구동하지만, Hayabusa는 `convert_to_fast_match` 함수를 통해 와일드카드의 위치를 식별하고 이를 더 가벼운 매칭 유형으로 변환한다.

변환을 위해 Hayabusa는 내부적으로 `FastMatch`라는 열거형(Enum) 구조를 사용한다.

```rust
// src/detections/rule/fast_match.rs
pub enum FastMatch {
    Exact(String),      // 정확히 일치
    StartsWith(String), // 전방 일치
    EndsWith(String),   // 후방 일치
    Contains(String),   // 부분 일치
    AllOnly(String),
}
```

`convert_to_fast_match` 함수는 규칙 문자열을 분석하여, 문자열의 맨 앞에만 와일드카드가 있는 경우(`*\cmd.exe`) 이를 `FastMatch::EndsWith("cmd.exe")`로 변환한다. 양끝에 와일드카드가 있다면 `Contains`로, 맨 뒤에만 있다면 `StartsWith`로 분류하며, 와일드카드가 없는 경우는 `Exact`로 처리한다. 와일드카드가 문자열 중간에 포함되어 단순 메서드로 처리가 불가능한 경우에만 예외적으로 정규표현식을 사용하도록 설계되어 있다.

```rust
// src/detections/rule/fast_match.rs
pub fn convert_to_fast_match(s: &str, ignore_case: bool) -> Option<Vec<FastMatch>> {
    // ... 생략 ...
    let wildcard_count = s.chars().filter(|c| *c == '*').count();

    if s.starts_with('*') && s.ends_with('*') && wildcard_count == 2 {
        // 양끝에 와일드카드가 있는 경우 Contains로 변환
        // ... 생략 ...
    } else if s.starts_with('*') && wildcard_count == 1 {
        // 맨 앞에만 와일드카드가 있는 경우 EndsWith로 변환
        return Some(vec![FastMatch::EndsWith(s[1..].replace(r"\", r""))]);
    }
    // ... 생략 ...
}
```

조건 변환이 완료되면, 실제 이벤트 로그의 필드 값과 대조하는 작업은 `check_fast_match` 함수가 수행한다. 이 함수는 앞서 분류된 `FastMatch` 타입에 따라 Rust 문자열 라이브러리의 표준 내장 메서드인 `ends_with`, `starts_with`, `contains` 등을 직접 호출하여 문자열을 비교한다.

```rust
// src/detections/rule/fast_match.rs
pub fn check_fast_match(...) -> Option<bool> {
    // ... 생략 ...
    match &fast_matcher {
        FastMatch::Exact(s) => Some(eq_ignore_case(event_value_str, s)),
        FastMatch::StartsWith(s) => {
            Some(event_value_str.starts_with(s)) // 전방 일치 연산
        }
        FastMatch::EndsWith(s) => {
            Some(event_value_str.ends_with(s)) // 후방 일치 연산
        }
        FastMatch::Contains(s) | FastMatch::AllOnly(s) => {
            Some(utils::contains_str(&event_value_str.to_lowercase(), s)) // 부분 일치 연산
        }
    }
    // ... 생략 ...
}
```

결과적으로 메인 분석 엔진은 연산 비용이 높은 정규표현식 연산을 거치지 않고, 가벼운 표준 문자열 대조만으로 악성 패턴의 포함 여부를 판별한다. 이를 통해 CPU 자원 소모를 최소화하고 대용량 로그 환경에서도 탐지 속도를 안정적으로 유지할 수 있다.

## 3. Normalization & Enrichment

탐지 단계를 거쳐 위협으로 식별된 원시 로그 데이터는 분석가가 직관적으로 이해하고 후속 조치를 취할 수 있도록 가공되어야 한다. 이 단계에서는 파편화된 필드 명칭을 통일하는 정규화(Normalization)와 로그 데이터에 위협 컨텍스트를 추가하는 정보 보강(Enrichment)이 이루어진다.

이해를 돕기 위해 Windows 이벤트 로그에서 사용자 이름이 기록되는 방식을 예로 들 수 있다. Windows 로그는 동일한 의미의 데이터라도 이벤트 ID나 채널에 따라 `SubjectUserName`, `TargetUserName`, `AccountName` 등 필드명이 제각각으로 기록된다.

```text
// 필드 정규화 매핑 예시 (rules/config/eventkey_alias.txt)
User, Event.EventData.SubjectUserName
User, Event.EventData.TargetUserName
User, Event.EventData.AccountName
```

Hayabusa는 이를 `%User%`와 같은 단일 명칭으로 통합하여 분석의 편의성을 제공한다. 관련 로직은 `src/detections/message.rs` 파일의 `parse_message` 함수에 구현되어 있다. 이 함수는 출력 프로파일이나 규칙에 지정된 플레이스홀더(`%User%`)를 탐색하고, 설정된 매핑 테이블을 참조하여 실제 원본 로그의 필드 경로로 치환해 값을 추출한다.

```rust
// src/detections/message.rs
pub fn parse_message(...) -> (CompactString, Vec<CompactString>) {
    // ... 생략 ...
    for caps in ALIASREGEX.captures_iter(&return_message) {
        let target_str = // ... '%User%' 등에서 괄호를 떼어내고 'User' 추출 ...
        
        // eventkey_alias 맵핑 테이블을 참조하여 원본 필드명으로 치환
        let array_str = if let Some(_array_str) = eventkey_alias.get_event_key(target_str) {
            _array_str.to_string()
        } else {
            format!("Event.EventData.{target_str}")
        };
        // ... 생략 ...
    }
    // ... 생략 ...
}
```

필드 통합과 더불어, 난해한 데이터 값을 읽기 쉬운 형태로 변환하거나 외부 정보를 결합하는 보강(Enrichment) 작업이 병행된다. 크게 세 가지 주요 처리 로직으로 나뉜다.

첫째, 로그에 기록된 에러 코드나 16진수 값을 평문으로 변환한다. `src/detections/field_data_map.rs` 파일에 구현된 `convert_field_data` 함수를 통해 `0xc0000234`와 같은 16진수 오류 코드를 `ACCOUNT LOCKED`와 같은 직관적인 문자열로 치환하여 분석가의 식별 속도를 높인다.

둘째, 공격자가 난독화를 위해 사용하는 Base64 인코딩 문자열을 자동으로 탐지하고 디코딩한다. `src/timeline/extract_base64.rs` 파일의 구현을 통해 `CommandLine`이나 `ScriptBlockText` 필드에 포함된 Base64 데이터를 추출한다. 이후 추출된 페이로드가 `UTF-8`, `UTF-16 LE` 등 어떤 인코딩 형식을 사용하는지 판별하여 디코딩된 평문을 타임라인 결과에 추가한다.

```rust
// src/timeline/extract_base64.rs
impl Base64Data {
    fn new(token: &str, payload: &[u8]) -> Self {
        // 추출한 페이로드의 인코딩 형식을 판별하여 구조체로 반환
        if is_utf16_le(payload) {
            let s = utf16_le_to_string(payload).unwrap();
            return Base64Data::Utf16Le(token.to_string(), s);
        } else if is_utf8(payload) {
            let s = str::from_utf8(payload).unwrap();
            return Base64Data::Utf8(token.to_string(), s.to_string());
        }
        // ... 생략 ...
    }
    // ... 생략 ...
}
```

셋째, IP 주소 기반의 위치 정보 보강이 이루어진다. 추출된 로그 필드 내에 IP 주소가 존재할 경우, `src/options/geoip_search.rs`에 구현된 로직을 통해 외부 GeoIP 데이터베이스(MaxMind 등)를 조회한다. 이를 통해 기존 원시 로그에는 존재하지 않았던 자율시스템번호(ASN), 국가, 도시 정보를 확인하고, 이를 `SrcASN`, `SrcCountry` 등의 새로운 필드로 생성하여 최종 결과물에 덧붙인다.

이러한 정규화 및 보강 과정을 거친 데이터는 분석가가 복잡한 원본 로그의 구조를 일일이 파악할 필요 없이, 단일화된 타임라인(CSV/JSONL) 상에서 즉시 시스템의 위협 컨텍스트를 파악할 수 있는 형태로 출력된다.

# 부록: Hayabusa 주요 탐지 이벤트 로그 및 Sigma Rule

Hayabusa가 중점적으로 분석하는 핵심 이벤트 로그와, 실제 Sigma Rule에서 위협을 식별하기 위해 대조하는 탐지 조건의 예시는 다음과 같다.

*   **Event ID 4688 (Security) 및 Sysmon 1: 프로세스 생성**
    *   **탐지 규칙 예시:** `CommandLine: '*\powershell.exe -enc*'` 또는 `Image: '*\cmd.exe'`
    *   **분석 관점:** 악성코드나 해커가 시스템에서 실행하는 명령어를 식별한다. Hayabusa는 `CommandLine` 및 `Image` 필드를 검사하여 난독화된 파워쉘 인자가 사용되었는지, 혹은 정상 시스템 프로세스(LOLBins)를 악용하는 패턴이 존재하는지 대조한다.

*   **Event ID 4624 및 4625 (Security): 성공/실패한 계정 로그온**
    *   **탐지 규칙 예시:** `LogonType: 3` (네트워크 로그온) 조건과 `TargetUserName: 'Administrator'` 조합
    *   **분석 관점:** 내부망 횡적 이동(Lateral Movement) 및 무차별 대입 공격을 탐지한다. Hayabusa는 `LogonType` 값을 필터링하여 원격 접속 여부를 판별하고, `TargetUserName`과 `SrcIP`를 조합하여 특정 IP에서 반복적인 로그온 실패가 발생하는지 검사한다.

*   **Event ID 7045 (System): 새로운 서비스 등록**
    *   **탐지 규칙 예시:** `ImagePath: '*\AppData\Local\Temp\*'` 또는 `ImagePath: '*%COMSPEC%*'`
    *   **분석 관점:** 악성코드가 재부팅 후에도 지속성을 확보하기 위해 백도어 서비스를 등록하는 행위를 탐지한다. Hayabusa는 `ImagePath` 필드를 검사하여 비정상적인 임시 폴더 경로에서 실행 파일이 등록되었는지, 혹은 서비스 등록에 cmd.exe가 직접 호출되었는지 확인한다.

*   **Event ID 4104 (PowerShell Operational): 스크립트 블록 로깅**
    *   **탐지 규칙 예시:** `ScriptBlockText: '*FromBase64String*'` 또는 `ScriptBlockText: '*Invoke-Mimikatz*'`
    *   **분석 관점:** 파일 없이 메모리 상에서 악성 스크립트를 실행하는 파일리스 공격을 추적한다. Hayabusa는 `ScriptBlockText` 필드에 기록된 파워쉘 원문을 대상으로 난독화 해제 함수나 알려진 악성 모듈 이름이 존재하는지 문자열 대조를 수행한다.

*   **Event ID 4720 (Security): 로컬 사용자 계정 생성**
    *   **탐지 규칙 예시:** `TargetUserName: '*$'`
    *   **분석 관점:** 공격자가 시스템 내부에 지속성을 유지하기 위해 임의의 백도어 계정을 생성하는 행위를 탐지한다. Hayabusa는 `TargetUserName` 필드를 확인하여 이름 끝에 특수문자가 포함되는 등의 비정상적인 명명 규칙을 가진 계정이 생성되었는지 검사한다.

*   **Event ID 4732 (Security): 보안 로컬 그룹에 멤버 추가**
    *   **탐지 규칙 예시:** `TargetSid: 'S-1-5-32-544'` (Administrators 그룹 SID)
    *   **분석 관점:** 공격자가 일반 계정에 관리자 권한을 부여하여 권한 상승을 시도하는 행위를 탐지한다. Hayabusa는 `TargetSid`를 검사하여 높은 권한의 그룹에 새로운 계정이 편입되는 행위를 대조한다.

*   **Event ID 5145 (Security): 네트워크 공유 파일 접근**
    *   **탐지 규칙 예시:** `ShareName: '*\C$'` 및 `RelativeTargetName: '*\Windows\System32\*'`
    *   **분석 관점:** 랜섬웨어 확산이나 중요 시스템 파일에 대한 비정상적인 원격 접근을 추적한다. Hayabusa는 접근한 공유 폴더 경로(`ShareName`)와 파일명(`RelativeTargetName`)을 조건으로 대조하여 중요 데이터에 대한 악의적인 접근 시도를 식별한다.
