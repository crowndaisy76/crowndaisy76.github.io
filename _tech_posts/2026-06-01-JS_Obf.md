자바스크립트 기반 악성코드는 대부분 탐지 우회와 분석 지연을 목적으로 난독화 과정을 거친다. 난독화된 스크립트를 분석가가 수동으로 역공학하는 방식은 시간과 자원 측면에서 효율성이 매우 떨어진다. 따라서 실제 위협 분석 환경에서는 이를 자동화하여 해제해 주는 역난독화 도구의 활용이 필수적이다.

이 글에서는 가장 널리 사용되는 자바스크립트 난독화 오픈소스인 [javascript-obfuscator](https://github.com/javascript-obfuscator/javascript-obfuscator)의 내부 동작 원리를 상세히 분석한다.


# AST(Abstract Syntax Tree) 개념 설명

실제 코드 분석에 앞서, AST가 무엇인지를 먼저 이해해야 한다. AST는 간단히 말해서 코드의 문법 구조를 트리 형태로 변환한 객체다.

사람이 작성한 자바스크립트 소스코드는 컴퓨터 입장에서는 단순한 문자열에 불과하다. 컴파일러나 난독화 도구가 이 코드를 분석하고 조작하려면, 문자열을 의미 있는 단위로 쪼개고 계층 구조로 정렬하는 과정이 필요하다. 이때 자바스크립트 텍스트를 파싱하여 트리 형태로 정형화한 결과물이 바로 AST다.

이 개념을 가장 직관적으로 이해하는 방법은 파서 라이브러리를 활용해 직접 코드를 변환해 보는 것이다. 여기서는 자바스크립트 생태계에서 널리 쓰이는 가벼우면서도 강력한 파서인 `acorn`을 사용한다.

아래 코드는 `myCode`라는 변수에 담긴 자바스크립트 함수를 AST로 변환하는 간단한 Node.js 스크립트다.

```JavaScript
const acorn = require('acorn');

const myCode = `
function add(a, b) {
  return a + b;
}
`;

const ast = acorn.parse(myCode, { ecmaVersion: 2020 });

console.log(JSON.stringify(ast, null, 2));

```

## AST JSON 결과 구조 분석

출력된 JSON을 위에서부터 차근차근 따라가면 코드가 어떻게 트리 구조로 형상화되었는지 알 수 있다. 가장 핵심이 되는 노드들을 쪼개어 보면 다음과 같다.

* **Program**: 트리 구조의 최상위 루트 노드다. 전체 소스코드 파일 자체를 의미한다.
* **FunctionDeclaration**: `function add(a, b)` 구조를 통째로 정의하는 노드다. 내부에는 함수의 이름(`id`), 매개변수(`params`), 그리고 함수의 실제 동작 영역(`body`)을 자식 노드로 품고 있다.
* **Identifier**: 변수명이나 함수명 같은 고유한 식별자를 나타낸다. JSON을 보면 함수의 이름인 `add`, 그리고 매개변수인 `a`와 `b`가 모두 이 `Identifier` 타입으로 변환된 것을 확인할 수 있다.
* **BlockStatement**: 중괄호 `{ ... }`로 감싸진 함수의 내부 실행 블록을 의미한다.
* **ReturnStatement**: 값을 반환하는 `return` 구문을 나타내며, 반환할 대상 데이터는 `argument` 속성에 자식 노드로 매핑된다.
* **BinaryExpression**: 이 트리의 가장 깊은 곳에 위치한 이항 연산 구문이다. `operator` 속성에는 더하기 기호(`+`)가 들어가고, 연산의 좌항(`left`)과 우항(`right`)에 각각 매개변수인 `a`와 `b`를 가리키는 `Identifier` 노드가 배치된다.

결과적으로 javascript-obfuscator 같은 난독화 도구는 이 트리를 탐색하면서 `Identifier` 노드를 찾아내어 알아볼 수 없는 무작위 문자열로 이름을 바꾸거나, `BinaryExpression` 구조를 복잡한 수학적 연산 공식 노드로 치환하는 방식으로 작동한다. 반대로 synchrony는 이 뒤틀린 트리 구조를 다시 탐색하여 규칙성을 찾아내고 본래의 깔끔한 노드 형태로 재조립하는 역할을 수행한다.

따라서 두 도구의 오픈소스 내부 코드를 이해하기 위해서는 이 AST 노드들을 어떻게 탐색하고 조작하는지 아는 것이 핵심이다.

# javascript-obfuscator 분석

javascript-obfuscator는 JavaScript를 난독화하는 데 사용되는 오픈소스이다.
난독화 파이프라인은 크게 세 가지 단계로 나뉘어 순차적으로 진행된다.

1. **Parsing**: 입력된 원본 자바스크립트 소스코드 문자열을 구문 분석기인 `acorn`을 통해 구조화된 데이터인 AST로 변환한다. 이 단계가 완료되면 코드는 제어가 가능한 노드 단위의 트리 형태로 재조립된다.

2. **Transformation**: 생성된 AST의 노드들을 순회하며 실질적인 암호화 및 구조 뒤틀기를 수행한다. 핵심 오케스트레이터는 내부적으로 정의된 노드 변환 스테이지(NodeTransformationStage)의 시퀀스를 따른다. Initializing과 Preparing 단계를 거쳐 데드 코드 주입, 제어 흐름 평탄화, 문자열 배열 추출 및 치환 등의 세부 스테이지들이 정해진 순서대로 트리 구조를 정교하게 변형한다.

3. **Code Generation**: 모든 변환 스테이지를 거쳐 최종적으로 은닉화가 완료된 AST를 코드 생성기인 `escodegen`을 이용해 다시 실행 가능한 자바스크립트 소스코드 문자열로 재현한다. 이 과정에서 공백을 압축하는 컴팩트 옵션 등이 적용되어 최종 결과물이 도출된다.

## 1. Parsing

이 단계에서는 실질적인 난독화를 진행하기 앞서 원본 자바스크립트 코드를 컴퓨터가 구조적으로 조작할 수 있는 데이터 구조인 AST로 변환한다. 문자열 형태의 소스코드를 노드 단위의 트리 구조로 파싱해야만 이후의 변환 프로세스를 정교하게 제어할 수 있기 때문이다.

javascript-obfuscator 내부에서 이 파싱 로직의 게이트웨이 역할을 하는 핵심 클래스는 `src/ASTParserFacade.ts`이다.

```typescript
import * as acorn from 'acorn';
import * as ESTree from 'estree';
import chalk, { Chalk } from 'chalk';
import { importAttributesOrAssertions } from 'acorn-import-attributes';

const AcornParser = acorn.Parser.extend(importAttributesOrAssertions);

/**
 * Facade over AST parser `acorn`
 */
export class ASTParserFacade {
    // ... (일부 내부 유틸리티 변수 생략)

    /**
     * @param {string} sourceCode
     * @param {Options} config
     * @returns {Program}
     */
    public static parse(sourceCode: string, config: acorn.Options): ESTree.Program | never {
        const sourceTypeLength: number = ASTParserFacade.sourceTypes.length;

        for (let i: number = 0; i < sourceTypeLength; i++) {
            try {
                return ASTParserFacade.parseType(sourceCode, config, ASTParserFacade.sourceTypes[i]);
            } catch (error) {
                if (i < sourceTypeLength - 1) {
                    continue;
                }

                throw new Error(ASTParserFacade.processParsingError(sourceCode, error.message, error.loc));
            }
        }

        throw new Error('Acorn parsing error');
    }

    /**
     * @param {string} sourceCode
     * @param {acorn.Options} inputConfig
     * @param {acorn.Options["sourceType"]} sourceType
     * @returns {Program}
     */
    private static parseType(
        sourceCode: string,
        inputConfig: acorn.Options,
        sourceType: acorn.Options['sourceType']
    ): ESTree.Program {
        const comments: ESTree.Comment[] = [];
        const config: acorn.Options = {
            ...inputConfig,
            allowAwaitOutsideFunction: false,
            allowReserved: true,
            allowImportExportEverywhere: true,
            allowReturnOutsideFunction: true,
            allowSuperOutsideMethod: true,
            onComment: comments,
            sourceType
        };

        const program: acorn.Node & ESTree.Program = <acorn.Node & ESTree.Program>AcornParser.parse(sourceCode, config);

        if (comments.length) {
            program.comments = comments;
        }

        return program;
    }
}

```

이 코드는 오픈소스 파서인 `acorn`을 {% include wiki_link.html text="퍼사드 패턴(Facade Pattern)" url="/tech/Details/Facade" %}으로 감싸서 확장성 있고 안전하게 파싱을 수행하는 구조다. `acorn` 파서에 `import attributes` 지원을 위한 플러그인을 확장한 `AcornParser`를 정의하여 현대적인 자바스크립트 문법까지 완벽하게 소화할 수 있도록 설계되었다.

핵심 메서드인 `parse`의 동작을 살펴보면, 입력된 소스코드를 일반 스크립트(`script`) 방식과 {% include wiki_link.html text="ES 모듈" url="/tech/Details/ES" %}(`module`) 방식이라는 두 가지 `sourceType` 환경에서 유연하게 파싱을 시도한다. 내부의 `parseType` 메서드는 자바스크립트 유연성을 극대화하는 파싱 옵션들을 주입한 뒤, 실제 `AcornParser.parse`를 호출하여 ESTree 명세를 따르는 최상위 루트 노드인 `Program` 객체를 생성한다. 또한 이 과정에서 주석(`comments`) 데이터도 유실되지 않도록 정교하게 수집하여 트리에 병합하는 역할을 수행한다.

메인 컨트롤러인 `src/JavaScriptObfuscator.ts` 내부를 보면, 원본 문자열을 이 퍼사드 클래스의 `ASTParserFacade.parse` 메서드에 넘겨 완벽한 트리 구조로 전달받으며, 이렇게 빌드된 AST 데이터가 난독화의 본체인 다음 단계(Transformation) 파이프라인의 핵심 원재료로 쓰이게 된다.

## 2. Transformation
Parsing 단계를 거쳐 생성된 AST는 곧바로 실질적인 난독화 작업을 수행하는 트랜스포머 파이프라인으로 진입한다. javascript-obfuscator는 객체 지향적인 아키텍처와 컴포넌트의 책임을 명확히 분리하기 위해, 노드 변환 단계를 총 10개의 정교한 스테이지 시퀀스(`NodeTransformationStage`)로 나누어 순차적으로 처리한다.

각 스테이지는 트리 구조의 특정 문법 노드를 타깃으로 삼아 정해진 보안 규칙에 따라 변형을 가하며, 이전 단계의 변환 결과가 다음 단계의 입력 기틀이 되는 유기적인 흐름을 형성한다.

### Stage 1: Initializing

이 단계는 Parsing이 끝난 직후, 본격적인 난독화를 수행하기 전에 트리를 전처리하고 안정적인 상태로 정형화하는 시퀀스다. 원본 코드의 문법 구조를 안전하게 보존하면서, 무분별하게 파괴될 수 있는 메타데이터나 주석을 필터링하는 작업을 수행한다.

javascript-obfuscator 내부에서 이 초기화 및 주석 제어를 전담하는 핵심 컴포넌트는 `src/node-transformers/initializing-transformers/CommentsTransformer.ts` 파일이다. 실제 오픈소스 아키텍처 규칙에 기반한 핵심 구현 구조는 다음과 같다.

```typescript
import { inject, injectable, injectFromBase } from 'inversify';
import { ServiceIdentifiers } from '../../container/ServiceIdentifiers';
import * as ESTree from 'estree';

import { AbstractNodeTransformer } from '../AbstractNodeTransformer';
import { IVisitor } from '../../interfaces/node-transformers/IVisitor';
import { NodeTransformationStage } from '../../enums/node-transformers/NodeTransformationStage';
import { IRandomGenerator } from '../../interfaces/utils/IRandomGenerator';
import { IOptions } from '../../interfaces/options/IOptions';

@injectFromBase()
@injectable()
export class CommentsTransformer extends AbstractNodeTransformer {
    /**
     * @param {IRandomGenerator} randomGenerator
     * @param {IOptions} options
     */
    public constructor(
        @inject(ServiceIdentifiers.IRandomGenerator) randomGenerator: IRandomGenerator,
        @inject(ServiceIdentifiers.IOptions) options: IOptions
    ) {
        super(randomGenerator, options);
    }

    /**
     * @param {NodeTransformationStage} nodeTransformationStage
     * @returns {IVisitor | null}
     */
    public getVisitor(nodeTransformationStage: NodeTransformationStage): IVisitor | null {
        if (nodeTransformationStage !== NodeTransformationStage.Initializing) {
            return null;
        }

        return {
            enter: (node: ESTree.Node, parentNode: ESTree.Node | null): ESTree.Node | undefined => {
                return this.transformNode(node, parentNode);
            }
        };
    }

    /**
     * @param {Node} node
     * @param {Node | null} parentNode
     * @returns {Node}
     */
    public transformNode(node: ESTree.Node, parentNode: ESTree.Node | null): ESTree.Node {
        // 주석 보존 및 필터링 핵심 로직 처리 영역
        // node.leadingComments 또는 node.trailingComments 내의 '@license', '@preserve' 단어 검증
        return node;
    }
}

```

#### 코드 및 동작 메커니즘 분석

* **싱글톤 아키텍처 결합**: javascript-obfuscator는 프레임워크의 결합도를 낮추기 위해 `inversify` 패턴을 일관되게 활용한다. `AbstractNodeTransformer`를 상속받은 이 클래스는 `@injectFromBase()`와 `@injectable()` 데코레이터를 통해 메인 가동 엔진의 컨테이너 시스템에 안전하게 등록된다.
* **스테이지 필터링 체계**: `getVisitor` 메서드는 전체 난독화 파이프라인 중 오직 `NodeTransformationStage.Initializing` 단계에서만 주석 변환기가 동작하도록 인터페이스를 차단한다. 만약 현재 실행 중인 엔진의 스테이지가 초기화 단계가 아니라면 즉시 `null`을 반환하여 불필요한 트리 탐색 비용을 최소화한다.
* **주석 메타데이터 정제(Filter)**: 자바스크립트는 정적 분석과 동적 탐지를 지연시키기 위해 대다수의 무의미한 공백과 일반 주석(`//`, `/* */`)을 제거해야 한다. 그러나 오픈소스 라이선스 명시나 크레딧과 같이 법적으로 보존해야 하는 특정 특수 주석들이 존재한다. `transformNode` 로직은 AST 노드의 `leadingComments`와 `trailingComments` 프로퍼티를 전수 조사하여, 내부에 **`@license`** 또는 **`@preserve`** 문구가 포함되어 있는지를 정밀 검증한다. 이 규칙에 일치하는 주석 노드는 지우지 않고 안전한 격리 컨텍스트로 이주시켜 보존하고, 그 외의 일반 분석용 주석들은 트리가 비대해지는 것을 막기 위해 이 단계에서 일제히 소거한다.

결과적으로 이 초기화 단계를 깔끔하게 마치고 나서야 비로소 자바스크립트 트리는 외부 문자열 노이즈가 완벽하게 정제된 순수 실행 노드 상태가 되며, 다음 단계인 Preparing 단계로 안전하게 넘어갈 수 있게 된다.

### Stage 2: Preparing

이 단계는 AST 트리가 구축된 이후 본격적인 코드 변환을 수행하기 전, 스코프와 변수의 상호 참조 관계를 분석하고 난독화 대상에서 제외할 노드들을 사전에 차단하는 준비 시퀀스다. Static analysis 작업을 통해 전체 식별자의 유효 범위와 전역 변수 체인을 파악하는 역할을 수행한다.

javascript-obfuscator 내부에서 이 처리를 담당하는 대표적인 컴포넌트는 `src/node-transformers/preparing-transformers/ObfuscatingGuardsTransformer.ts` 파일이다. 실제 프로젝트 아키텍처 규격에 따른 구현 형태는 다음과 같다.

```typescript
}

```

#### 코드 및 동작 메커니즘 분석

* **Stage 매핑 차단 체계**: `getVisitor` 메서드는 오직 `NodeTransformationStage.Preparing` 상태일 때만 활성화된다. 만약 파이프라인의 현재 시퀀스가 `Preparing` 단계가 아니라면 즉시 `null`을 반환하여 불필요한 AST 탐색을 차단한다.


* **Scope analysis 및 환경 제어**: 이 단계에서는 내부적으로 `ScopeAnalyzer` 등을 연동하여 변수가 선언되고 사용되는 상호 참조 그래프를 매핑한다. 또한 블랙리스트 패턴이나 사용자 옵션 수식을 검증하여 전역 환경 변수인 `process.env` 등 난독화가 수행되면 오작동을 유발할 수 있는 식별자 체인을 사전에 보호 리스트로 분류한다.


* **Obfuscating guards 설정**: `transformNode` 로직은 수집된 규칙에 따라 노드의 메타데이터 프로퍼티를 동적으로 세팅한다. 은닉 처리를 우회해야 할 타깃으로 식별된 노드는 `ignoredNode` 플래그를 할당받아 이후의 파이프라인 스테이지에서 변형되지 않도록 안전 가드가 걸리게 된다.


이러한 Preparing 과정이 완벽히 완료되어야만 트리의 모든 스코프 구조와 가드가 정립되며, 뒤이어 진행될 실질적인 변형 단계로 안전하게 진입할 수 있다.

### Stage 3: DeadCodeInjection

이 단계는 분석가가 프로그램의 실제 제어 흐름을 정적 또는 동적으로 추적하는 것을 방해하기 위해, 실행 결과에는 아무런 영향을 주지 않으면서 코드의 외형적인 복잡도만 기하급수적으로 늘리는 가짜 로직 블록(더미 코드)을 난입시키는 시퀀스다.

* **가짜 노드 인젝션**: 조건이 충족되면 함수 선언이나 루프 블록 내부에 결코 실행되지 않거나(Opaque Predicate 기법) 혹은 실행되어도 부작용이 없는 가짜 수식, 조건문 구조를 동적으로 생성하여 기존 자식 노드 배열 사이에 교묘하게 삽입한다. 이로 인해 코드의 구조적 부피가 크게 늘어나 정적 분석 장비와 인간 분석가 모두에게 큰 분석 지연을 유발한다.

이 과정이 완료되면 프로그램의 겉모양은 무의미한 가짜 분기문들로 가득 차게 되며, 뒤이어 가장 강력한 왜곡 기법인 ControlFlowFlattening 단계로 진입할 준비를 마치게 된다.

### Stage 4: ControlFlowFlattening

이 단계는 자바스크립트 프로그램의 직관적인 선형 실행 구조(`for`, `while`, `if-else` 등)를 완전히 해체하여, 무작위로 뒤섞인 거대한 하나의 루프와 상태값을 가진 `switch-case` 구조로 평탄화(Flattening)하는 시퀀스다. javascript-obfuscator가 제공하는 여러 우회 및 은닉화 기술 중 원본 코드의 실행 흐름을 가장 강력하게 왜곡하는 핵심 스테이지다.

javascript-obfuscator 내부에서 이 고난도 제어 구조 뒤틀기를 전담하는 대표적인 트랜스포머는 `src/node-transformers/control-flow-transformers/BlockStatementControlFlowTransformer.ts` 파일이다. 실제 프로젝트 아키텍처 규격에 따른 핵심 구현 형태는 다음과 같다.

#### 코드 및 동작 메커니즘 분석

* **Stage 매핑 차단 체계**: `getVisitor` 메서드는 오직 제어 흐름 왜곡 타이밍인 `NodeTransformationStage.ControlFlowFlattening` 시퀀스에서만 동작을 허용한다. 해당 단계를 거치지 않는 다른 파이프라인 연산 중에는 `null`을 반환해 트리의 구조를 불필요하게 탐색하지 않도록 격리한다.
* **선형 실행 블록의 분해 및 셔플**: `transformNode` 로직은 AST 트리 상의 독립적인 실행 영역(예: 5줄 이상의 연속된 구문을 가진 블록)을 타깃팅한다. 원래라면 순차적으로 실행되어야 할 낱개의 구문들을 개별 상태 번호가 부여된 노드로 완전히 분해한 뒤, 런타임 상의 상태 천이 시퀀스 데이터를 무작위(`shuffledKeys`)로 뒤섞는다.
* **상태 머신 트랩 구성**: 분해된 구문들을 하나의 `switch-case` 문 내부에 흩뿌려 배치하고, 이 switch 문을 무한 루프(`while(true)`) 노드로 감싼다. 루프 내부에는 다음번에 올바르게 실행되어야 할 case 번호를 기억하고 업데이트하는 제어 변수(State Variable)와 문자열 기반 가이드 노드(`BlockStatementControlFlowFlatteningNode`)를 이식한다.

이 변환 단계를 완료하면 위에서 아래로 정직하게 흐르던 원본 코드가 거대한 상태 머신 트랩으로 변모하므로, 정적 분석 도구는 실행 흐름 그래프(CFG)를 그릴 수 없게 되고 인간 분석가 역시 실행 흐름을 추적하기가 극도로 난해해진다. 제어 흐름 구조가 평탄화되면 트리는 객체와 속성 데이터를 은닉하는 다음 시퀀스인 RenameProperties 단계로 연결된다.

### Stage 5: RenameProperties

이 단계는 객체의 속성(Property) 명칭이나 클래스 내부의 필드 및 메서드 이름을 알아볼 수 없는 고유 기호로 강제 치환하는 시퀀스다. 식별자 이름뿐만 아니라 객체의 내부 구조까지 매글링(Mangling)하여 정적 분석을 한층 더 방해하는 역할을 수행한다.

javascript-obfuscator 내부에서 이 처리를 전담하는 핵심 컴포넌트는 `src/node-transformers/rename-properties-transformers/RenamePropertiesTransformer.ts` 파일이다. 실제 프로젝트 아키텍처 규격에 따른 구현 형태는 다음과 같다.

이 단계를 거치면 객체 구조의 가시성이 완전히 은닉되며, 다음으로 리터럴 값을 복잡한 연산식 형태로 조작하는 Converting 단계로 파이프라인이 이어진다.

### Stage 6: Converting

이 단계는 사람이 읽고 직관적으로 식별할 수 있는 명시적인 값(리터럴, 템플릿 문자열, 불리언 등)을 실행은 가능하지만 분석가는 해석하기 난해한 구문 구조로 변형하는 시퀀스다. AST 상의 Primitive Value 노드들을 연산식이나 시스템 구조를 활용한 연쇄 노드로 확장하는 역할을 수행한다.

javascript-obfuscator 내부에서 이 가공 작업을 전담하는 컴포넌트 중 하나는 `src/node-transformers/converting-transformers/TemplateLiteralTransformer.ts` 파일이다. 실제 프로젝트 아키텍처 규격에 따른 구현 형태는 다음과 같다.

```typescript
import { inject, injectable, injectFromBase } from 'inversify';
import { ServiceIdentifiers } from '../../container/ServiceIdentifiers';
```

#### 코드 및 동작 메커니즘 분석

* **Stage 매핑 차단 체계**: `getVisitor` 메서드는 `NodeTransformationStage.Converting` 시퀀스 인터페이스에서만 호출되도록 잠금 장치가 걸려 있다. 노드 가공 타이밍이 아닐 때는 즉시 `null`을 반환하여 트리의 오염을 방지한다.
* **Literal 데이터의 구조 분해**: `transformNode` 로직은 AST 상의 원시적인 리터럴 관련 노드들을 수집한다. 이 디렉터리 내의 형제 컴포넌트들과 함께 작동하며 다음과 같은 치환 연산을 병렬적으로 처리한다.
  * 불리언 리터럴인 `true`를 빈 배열과 부정 연산자가 결합된 `!![]` 노드로, `false`를 `![]` 노드로 뒤튼다.
  * 숫자 리터럴인 `10`을 `0x2 + 0x9 - 0x1` 같이 16진수와 사칙연산 기호가 교차하는 `BinaryExpression` 노드로 확장한다.


* **문자열 가독성 해체**: 상기 소스코드의 `TemplateLiteralTransformer`는 변수와 문자열이 결합된 백틱 형태 구문(예: ``hello ${name}``)을 탐색한다. 이를 일반적인 문자열 조각 노드들로 낱낱이 쪼갠 뒤, 더하기(`+`) 연산자로 무수히 복잡하게 이어진 문자열 가산 트리 구조로 재조립하여 코드의 가독성을 전면 파괴한다.

이 단계를 거치면 소스코드 내부의 직관적인 데이터 값들이 복잡한 논리 및 수학 연산 트랩으로 가려지게 되며, 파이프라인은 식별자 명칭들을 일제히 매글링하는 RenameIdentifiers 단계로 이어진다.

### Stage 7: RenameIdentifiers

이 단계는 소스코드 내에 선언되고 참조되는 변수명, 함수명, 매개변수명 등 모든 식별자(Identifier)의 이름을 의미 없는 난해한 문자열로 일제히 치환하는 시퀀스다. 코드의 논리적 기능은 유지하면서 텍스트 기반의 가독성을 완전히 무력화하는 역할을 수행한다.

* **Stage 매핑 차단 체계**: `getVisitor` 메서드는 오직 식별자 변경 타이밍인 `NodeTransformationStage.RenameIdentifiers` 시퀀스에서만 동작하도록 제한된다. 다른 스테이지 영역의 연산 중에는 `null`을 반환하여 트리의 탐색 오버헤드를 방지한다.

* **식별자 명명 규칙 적용**: 수집된 `Identifier` 노드들은 사용자가 설정한 식별자 생성 옵션(`identifierNamesGenerator`)에 따라 변환된다. 기본적으로 16진수 형태(`_0x5a2b`)로 덮어쓰거나, 전체 코드 크기를 줄이기 위해 문자 열거 방식(`a`, `b`, `c`)을 채택하여 소스코드 내부의 의미 있는 상징성들을 완전히 소거한다.

이 과정이 완료되면 소스코드 내부의 인자 체인이 기호화되어 의미 파악이 완전히 불가능해지며, 파이프라인은 중요 문자열 데이터를 한곳으로 모아 은닉하는 StringArray 단계로 연결된다.

### Stage 8: StringArray

이 단계는 소스코드 전반에 흩어져 있는 모든 중요 문자열 리터럴 노드를 AST 트리에서 추출하여 하나의 거대한 '중앙 집중식 배열 저장소'로 이주시킨 뒤, 원래 문자열이 있던 자리에는 배열을 호출하는 프록시 함수(Wrapper) 노드를 심어놓는 시퀀스다. 소스코드 내부의 핵심 로직과 민감한 문자열 데이터를 외부에서 쉽게 정적 분석(Static analysis)하지 못하도록 은닉하는 역할을 수행한다.

javascript-obfuscator 내부에서 이 강력한 문자열 다발 추출 가공 프로세스를 전담하는 핵심 컴포넌트는 `src/node-transformers/string-array-transformers/StringArrayTransformer.ts` 파일이다. 실제 프로젝트 아키텍처 규격에 따른 주요 구현 형태는 다음과 같다.

#### 코드 및 동작 메커니즘 분석

* **Stage 매핑 차단 체계**: `getVisitor` 메서드는 오직 문자열 대량 은닉 타이밍인 `NodeTransformationStage.StringArray` 시퀀스에서만 활성화되도록 제한 제어가 걸려 있다. 문자열 추출 및 치환 타이밍이 아닐 때는 즉시 `null`을 반환하여 트리의 탐색 오버헤드를 근본적으로 차단한다.


* **문자열 리터럴 전수 수집 및 필터링**: `transformNode` 로직은 AST 트리를 순회하면서 `Literal` 노드 중에서도 순수하게 텍스트 정보를 품고 있는 `String Literal` 노드를 수집한다. 이때 시스템 예약어나 주석 가드, 혹은 사용자가 지정한 배제 리스트(`reservedStrings`)에 포함되지 않는 순수 평문 문자열들만 선별하여 프로젝트 전역에서 관리되는 거대한 `StringArrayStorage`로 안전하게 하이재킹(Extraction)한다.


* **배열 저장소 및 실시간 복호화 프록시 체인 설계**: 추출된 소스코드의 본래 자리에는 단순히 `stringArray[0]` 형태로 치환되는 트랩을 파괴하기 위해 고도의 런타임 래퍼 프록시 노드(`StringArrayCallNode`)를 이식한다. 이 과정에서 중앙 배열 저장소 데이터는 Base64나 RC4 같은 특수 암호화 알고리즘 기반 데이터 스트링으로 변환(Encoding)되며, 런타임 시 정적 해독을 마비시키기 위해 배열 인덱스를 강제로 주기적으로 시프트(Shift) 회전시키는 가짜 오프셋 연산 함수 노드(`StringArrayRotateFunction`)까지 결합하여 은닉을 완성한다.

이 단계를 완수하면 프로그램 내의 모든 중요한 평문 단어 정보가 일차원적으로 노출되지 않고 거대한 기호화 배열 장벽 속에 숨겨지게 되며, 뒤이어 뒤틀려진 노드 구문들을 콤마 연산자 등으로 묶고 압축하는 Simplifying 단계로 파이프라인이 이어진다.

### Stage 9: Simplifying

이 단계는 앞선 트랜스포머들에 의해 노드가 변형되고, 분해되면서 비대해진 트리의 구문 구조를 최적화하고 결합하여 가독성을 한층 더 떨어뜨리는 시퀀스다. 복잡해진 노드들을 논리적으로 동일하지만 텍스트 표현상 더 복잡하고 얽힌 형태로 압축함으로써 분석가의 눈을 피하고, 최종 결과물의 구조적 난독화를 완성한다.

javascript-obfuscator 내부에서 이 압축 및 단순화 작업을 전담하는 핵심 컴포넌트는 `src/node-transformers/simplifying-transformers/ExpressionStatementsMergeTransformer.ts` 파일이다. 실제 프로젝트 아키텍처 규격에 따른 구현 형태는 다음과 같다.


#### 코드 및 동작 메커니즘 분석

* **Stage 매핑 차단 체계**: `getVisitor` 메서드는 오직 `NodeTransformationStage.Simplifying` 시퀀스에서만 동작하도록 제한된다. 다른 스테이지 영역에서는 즉시 `null`을 반환하여 트리의 탐색 성능을 보호한다.
* **코드 라인 및 구조 압축**: `transformNode` 로직은 AST 트리 상에서 인접해 있는 `ExpressionStatement` 노드들을 탐색한다. 이들을 단순히 순차적으로 실행하게 두지 않고, 자바스크립트의 콤마 연산자(Comma Operator)를 활용한 하나의 거대한 복합 표현식 노드로 강제 병합한다. 예를 들어 `a(); b(); c();` 형태의 문장을 `(a(), b(), c());`와 같은 단일 구문 노드로 변형하여 코드의 물리적 라인 수를 줄이고 분석가의 시각적 추적 흐름을 꼬아버린다.
* **불필요한 구조적 중복 제거**: 이 단계의 형제 컴포넌트인 `VariableDeclarationsMergeTransformer` 등과 결합하여, 분산 선언된 변수 노드들을 단일 `VariableDeclaration` 노드로 묶는 등의 작업을 통해 코드의 추상화 수준을 고의적으로 뒤튼다.

이 과정을 거치면 코드는 매우 밀도 높고 파편화된 복합 구문들의 덩어리가 되며, 분석가는 코드의 시작점과 종료점을 구분하기가 매우 어려워진다. 이제 모든 난독화 여정을 마무리하고 코드를 최종 출력하는 Finalizing 단계만이 남게 된다.

### Stage 10: Finalizing

이 단계는 모든 난독화 트랜스포머 파이프라인을 거쳐 심각하게 왜곡되고 분해된 AST 트리를 다시 실행 가능한 자바스크립트 소스코드 문자열로 재현하는 종착지다. 파싱 과정에서 수집된 주석 메타데이터를 정렬하고, 최종 코드 생성 과정에서 문법적 무결성을 확보하기 위해 지시어(Directive)를 재배치하는 등 규격화 작업을 수행한다.

javascript-obfuscator 내부에서 최종 코드 생성과 규격화를 담당하는 핵심 컴포넌트는 `src/node-transformers/finalizing-transformers/DirectivePlacementTransformer.ts` 파일이다. 실제 프로젝트 아키텍처 규격에 따른 구현 형태는 다음과 같다.

```typescript
        @inject(ServiceIdentifiers.IOptions) options: IOptions
    ) {
        super(randomGenerator, options);
    }

    /**
     * @param {NodeTransformationStage} nodeTransformationStage
     * @returns {IVisitor | null}
     */
    public getVisitor(nodeTransformationStage: NodeTransformationStage): IVisitor | null {
        if (nodeTransformationStage !== NodeTransformationStage.Finalizing) {
            return null;
        }

        return {
            enter: (node: ESTree.Node, parentNode: ESTree.Node | null): ESTree.Node | undefined => {
                return this.transformNode(node, parentNode);
            }
        };
    }

    /**
     * @param {Node} node
     * @param {Node | null} parentNode
     * @returns {Node}
     */
    public transformNode(node: ESTree.Node, parentNode: ESTree.Node | null): ESTree.Node {
        // 코드 최상단 지시어("use strict" 등)를 탐색하여 위치를 재조정하고 최종 문법 교정 수행
        return node;
    }
}

```

#### 코드 및 동작 메커니즘 분석

* **Stage 매핑 차단 체계**: `getVisitor` 메서드는 오직 `NodeTransformationStage.Finalizing` 단계에서만 활성화된다. 다른 모든 스테이지에서는 트리의 물리적 변경을 방지하기 위해 즉시 `null`을 반환한다.
* **Directive Placement 및 구조 규격화**: `transformNode` 로직은 변환 과정에서 노드 삽입/삭제로 인해 원래 위치를 이탈할 수 있는 `"use strict";`와 같은 지시어 노드들을 탐색한다. 자바스크립트 엔진이 지시어를 정상적으로 인식할 수 있도록, 지시어 노드를 다시 각 스코프의 최선두 위치로 정렬하고 재배치한다.
* **최종 소스코드 재생성 연동**: 이 단계가 완료되면 트리는 더 이상의 변환을 멈추고 `JavaScriptObfuscator`의 메인 컨트롤러로 전달된다. 마지막으로 내부적으로 통합된 `escodegen` 패키지가 이 최종 AST를 순회하며 사람이 다시는 원래 로직을 짐작할 수 없는, 기괴하게 압축되고 난독화된 자바스크립트 텍스트 문자열로 변환하여 출력하게 된다.

이처럼 10단계에 걸친 파이프라인을 통과하면, 원본 코드의 논리 구조는 유지하되 분석은 극도로 까다로워진 최종 AST가 생성된다.

## 3. Code Generation

난독화 파이프라인의 최종 단계는 변환된 AST를 다시 실행 가능한 자바스크립트 소스코드 문자열로 재현하는 Code Generation이다. 이 과정에서 코드 생성기인 `escodegen`은 트리 구조의 노드들을 역으로 순회하며, 자바스크립트 문법 규격에 맞는 텍스트 토큰과 포맷팅을 적용해 최종 결과물을 도출한다.

난독화기 내부에서 AST를 코드로 다시 변환하는 과정을 직관적으로 이해하기 위해, 앞서 `acorn`으로 파싱했던 AST 객체를 `escodegen`을 통해 다시 자바스크립트 코드로 복원하는 예시를 살펴본다.

```javascript
const escodegen = require('escodegen');

const ast = {
  "type": "Program",
  "start": 0,
  "end": 40,
  "body": [
    {
      "type": "FunctionDeclaration",
      "start": 1,
      "end": 39,

        "type": "Identifier",
        "start": 10,
        "end": 13,
        "name": "add"
      },
      "expression": false,
      "generator": false,
      "async": false,
      "params": [
        {
          "type": "Identifier",
          "start": 14,
          "end": 15,
          "name": "a"
        },
        {
          "type": "Identifier",
          "start": 17,
          "end": 18,
          "name": "b"
        }
      ],
      "body": {
        "type": "BlockStatement",
        "start": 20,
        "end": 39,
        "body": [
          {
            "type": "ReturnStatement",
            "start": 24,
            "end": 37,
            "argument": {
              "type": "BinaryExpression",

              "end": 36,

              },
```

```text
function add(a, b) {

```

### 동작 원리 및 특징

* **역변환 프로세스**: `escodegen`은 AST의 루트인 `Program` 노드부터 하위 자식 노드들을 재귀적으로 순회한다. `FunctionDeclaration` 노드를 만나면 `function` 키워드와 함수명을 출력하고, `params` 배열을 순회하며 매개변수를 쉼표로 연결하는 등 자바스크립트 구문 규칙에 맞춰 텍스트를 재구성한다. 이 과정에서 트리 상의 추상적인 노드들이 비로소 우리가 흔히 보는 문법 규격에 맞게 나열된다.
* **출력 최적화**: 난독화기는 이 단계에서 사용자 설정에 따라 출력물을 제어한다. 예를 들어 `compact` 옵션이 활성화되면 들여쓰기나 불필요한 공백을 모두 제거하여 소스코드의 전체 용량을 최소화하고, 단일 라인으로 코드를 압축하여 가독성을 극단적으로 떨어뜨린다.
* **구조적 규격화**: 난독화 파이프라인의 변환 과정에서 주석이나 위치 정보가 꼬인 경우에도, `escodegen`은 명세에 따라 정상적인 자바스크립트 문법을 강제로 복구하여 출력한다. 결과적으로 이 단계를 거치면, 기존의 논리 구조는 유지한 채 분석가는 도저히 읽기 힘든 형태의 최종 난독화 소스코드가 완성된다.

---

지금까지 자바스크립트 난독화의 표준인 javascript-obfuscator가 어떤 과정을 거쳐 코드를 보호하는지, 그 핵심 엔진인 파싱, 변환, 코드 생성의 3단계 파이프라인을 상세히 살펴보았다.

이 도구는 단순한 문자열 변환기를 넘어, AST 구조를 정교하게 뒤틀고 제어 흐름을 복잡하게 얽어내는 고도의 컴파일러적 기법을 사용한다. 우리가 분석한 10단계의 변환 스테이지들은 각각의 노드들을 분리하고 은닉하여, 정적 분석 도구와 분석가 모두에게 코드 해석의 난이도를 극단적으로 높이는 강력한 방어 기제로 작용한다.

이어서 다음 글에서는 난독화된 자바스크립트 코드를 AST 레벨에서 추적하여 원래의 형태로 정제해 내는 강력한 오픈소스 도구, synchrony의 내부 동작 원리를 분석하겠다.
